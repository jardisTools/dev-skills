#### Continuation §2 — Recipes 6–7: response shapes, bulk read


**Recipe 6 — Response shapes per operation (X-1)**

The Generator emits a fixed, minimal `setData(...)` payload per use-case kind — never the full aggregate (CQRS: Command mutates with a reference-value echo, Query reads with the projected graph). **`data` is flat:** the payload IS the business object and names its own type in the field `@type` — there is no handler-name level and no aggregate-root level around it, so `getData()['identifier']`, never `getData()['GetCounterByIdHandler']['counter']['identifier']`. Layout below for `Counter` (root business key named `counterIdentifier` in the generated code of the example domain; the key names follow the aggregate's business key).

| Use-case kind | Generated `setData(...)` shape (`@type`) |
|---|---|
| **Query ById (aggregate without a unique key) / By{UniqueKey}** (and hand-modelled single variants) | `['@type' => 'counter'] + get_object_vars(<CounterResponse>)` — the **root fields lie flat** in the array (`getData()['counterNumber']`), but **children stay typed `{Child}Response` objects** (a list of them for `many`, one object for `one`): read them with `->`, e.g. `getData()['registerRelation'][0]->register->obis`; `getData()['registerRelation'][0]['register']` throws at runtime (see Query projection below); nothing found → `[]` (empty payload, no `@type`) |
| **Query ByIds** (aggregate without a unique key) / **By{PluralKey}** (aggregate with a public unique key) | `['@type' => 'counterList', 'items' => <list<CounterResponse>>]` — every item is a typed `{Agg}Response` **object** (`$item->counterNumber`, children via `->` as well; `$item['counterNumber']` throws), **no `[0]` collapse**, no `total`/`limit`/`offset`; missing ids/keys → partial result, empty input → empty `items` |
| **List** (`{agg}List`, via the read facade) | a plain array `['items' => …, 'total' => …, 'limit' => …, 'offset' => …]` (not a `DomainResponse`); the generated route wraps it as `['@type' => 'counterList'] + $result` |
| **Create** | `['@type' => 'counter', 'counterIdentifier' => …]` — root business key only |
| **Set{Child}** / **Add{Child}** | `['@type' => 'counter', 'counterIdentifier' => …, '<childIdentifier>' => …]` — root key from the cmd-DTO + affected child key resolved via the aggregate walk |
| **Update** / **Remove** / **Remove{Child}** | `['@type' => 'counter', 'counterIdentifier' => …]` — root identity only (Remove{Child} skips the child key) |
| **Process** | `@type` (lcfirst process name), `@outcome` (the `gives.name` of the end node that ran, always) plus the **`gives`** of the end node that ran — nothing else is borrowed from the run. An end node is every node with a terminal edge (`{from, on, terminal: true}`) on a non-failure status; a process may have one per exit, each exit has its own form and its own name (the caller tells them apart by `@outcome`, never by which fields are present; `@type` stays the process name). `gives: {kind: identifier, name}` → the reference value of the command of that node (e.g. `['@type' => 'invoice', '@outcome' => 'invoiceIssued', 'invoiceIdentifier' => …]`); `gives: {kind: value, fields: [...]}` → exactly these fields, flat; a field may carry `ref` (a reference to an aggregate the process wrote, own `<Agg>` or foreign `<Subdomain>.<BC>.<Agg>`) and `list: true`; `gives: {kind: nothing, name}` → `@type` and `@outcome` only. The door builds the answer with one `answerFrom([<End node>::class => '<outcome>', …])` entry listing all end nodes as named candidates (the package takes the end node that ran last and writes its name as `@outcome`); a node that needs an earlier answer reads it through the typed getter of `<Name>Context`. A process that still carries `end`, `response`, `successOutput` or `answer` fails the load (CUT1, names the replacement). Status **200**, never 201 |
| **400 / 404 / 409 / 422** | `['@type' => 'validation', 'fields' => [{field, reason, message, messageKey}]]` / `['@type' => 'notFound', 'context']` / `['@type' => 'concurrencyConflict', 'reason', 'aggregate', 'context']` / `['@type' => 'ruleViolation', 'rule', 'messageKey', 'context']` |

Exactly one context of a response may carry data; the envelope mapper `TransformResponse` (package `jardissupport/response`) takes that payload as `data` and throws a `LogicException` when two contexts carry data — it never merges silently.

**`Remove{Child}` does not exist for every child.** A `Remove{Child}` command is only emitted when the child may actually be detached — a DEPEND leaf whose depend-FK is NOT NULL, and a `required` containment child, both get **no** remove mutation at all (rule and rationale: `generated-code-extend` §1). If the row above has no counterpart in your generated aggregate, that is the rule, not a gap.

Substitute the actual root identifier name (e.g. `counterId`, `meterNumber`) where the aggregate uses a different business key. Child responses use the child's business identifier (`<childIdentifier>`, e.g. `counterGatewayId`).

**Business-key resolution (G4 / X-2).** The Generator picks the root identifier by walking the entity for a Single-Column-Unique-Index on a NOT-NULL `string` column. If exactly one such column exists, that is the business key and surfaces in the response. If none exists, the response falls back to the internal `int` PK property (e.g. `counterGatewayId: int` for a keyless `counterGateway` child — not a defect, the only available identity). If multiple ambiguous candidates exist (X-2: two NOT-NULL-unique-string columns), the Build aborts — model an explicit single business key in the Schema instead of letting the response shape become non-deterministic.

**Query projection.** The Generator emits per BC a `{BC}/FieldMap.php` (ForceOverwrite — a pure naming container with one `{table}Columns()` method per BC table, the write-path DTO→column map; there is no `Fields()` method). The **read** projection (internal-PK strip where a business key exists, G4; root-id normalization; FK-column strip; pure-join collapse, F3.1) is aggregate-structural and runs at the **aggregate read edge (the query handler)**, not in FieldMap. The projected aggregate is the typed, recursive `{Agg}Response` class (`{BC}/Model/{Agg}/Query/Response/{Agg}Response.php`, children as `{Child}Response` properties — `public array $orderItem` is a list of `OrderItemResponse` objects); `getData()` spreads only the **root** level into the array, so child access is always `->`. The root `id` is carried by the projected record **only for an aggregate WITHOUT a public unique key** (normalized as `public int $id` on the `{Agg}Response`) — with a public unique key the key replaces it and the `{Agg}Response` has no `id` property (it starts with the key fields). A child entity without a business key of its own keeps its internal `id` (`public int $id` on its `{Child}Response`, the same fallback as the reference value above); a keyed child does not. This concerns the projected aggregate record only — the auto-**list** SELECT is not uniform: on an aggregate WITH a public unique key it leads with that key column `AS {keyField}` instead of `id` (the outward, key-first bulk-read recipe, Recipe 7 below); an aggregate WITHOUT one leads its list with `id`. `DateTimeImmutable` blade values stay inert — JSON/CLI serialization is the caller's job (G5).

**Command response** never carries domain state — only the reference value(s) the caller needs to address what just changed (event-sourcing / correlation). For the full state after a write, the caller issues the matching read-base query — `get{Agg}By{UniqueKey}` with the echoed business key, or `get{Agg}ById` (CQRS).

**Adding a custom field.** The `setData(...)` block sits inside the generated, hermetic operation `__invoke()` body — you do not edit it (V1). To enrich a Process answer, add a member to the object value (`gives: {kind: value, fields: [...]}`) of the end node that answers (an earlier node hands its value on only through the typed getter of `<Name>Context`, the end node names it again in its own `gives`); `BuildResponseData` puts `@type` in front, the answer carries `@outcome` as its first property, and the wire holds exactly the fields of that end node (an undeclared extra key never reaches the wire). Do not use the name `@type` for business fields.

**The success answer (the `gives` of the end node that ran).** A process names no answer of its own: the answer of the process is the `gives` of the end node that ran, one form per exit. There is no `end` on the process (the old form fails the load with CUT1 and the hint "the answer stands at the end node"), no derivation from the node it ends on and no `successOutput`. Set through the Process Designer (the pill at the end node shows the answer form; the `gives` editor of the node edits it, a field offers "Reference to …" and the switch "List") or MCP `save_process` (a save is a full replace, so carry the value you loaded). Each node says what it hands out with `gives: {kind: aggregate|identifier|value|nothing, name, ...}`; an end node is every node with a terminal edge `{from, on, terminal: true}` on a non-failure status. At an end node `gives.name` is mandatory for every kind (also `nothing`, `V-PROC-GIVES-1`) and is the free outcome name, delivered as `@outcome` (`V-PROC-OUTCOME-2`: `^[a-z][A-Za-z0-9]*$`, at most 64 characters).

| Form | `gives` of the end node | The 200 answer | Failure |
|---|---|---|---|
| identifier | `{"kind": "identifier", "name": "..."}` | `@type`, `@outcome` plus the reference value of the command of that node (the `{Command}Response`); counts as a field with `ref` on the aggregate of its command | `V-PROC-GIVES-2` (the kind must fit the node form; a command that works a list input off gives `value` with a list field, `identifier` is a blocker there) |
| fields | `{"kind": "value", "name": "...", "fields": [{"name": "orderNumbers", "type": "varchar", "list": true, "ref": "Order"}]}` | `@type`, `@outcome` plus exactly these fields, flat; `list` makes a list of the type, `ref` marks a reference to an aggregate root (own `<Agg>`, foreign `<Subdomain>.<BC>.<Agg>`) and does not change the type | `V-PROC-ANSWER-3` (`ref` names an aggregate root of the same domain, `type` fits its key type: the public unique key, without key `id`; `list` not with `json`); a missing non-nullable member is a `LogicException` → rollback, **500** |
| nothing | `{"kind": "nothing", "name": "..."}` (`name` is mandatory at an end node, `V-PROC-GIVES-1`) | `@type` and `@outcome` only (`{"@type":"<processName>","@outcome":"<gives.name>"}`), also for an exit that ends on a rule or event node | `V-PROC-ANSWER-1` when the exit follows a writer (see below) |

Rules of the answer (all blockers; the ids are listed in `BUILDER_VALIDATION.md`):

- **Reference duty (`V-PROC-ANSWER-1`).** For every aggregate X that a writer on a success path before the end node E writes (E itself included), E carries a field with `ref: X`. The field is a single field when on every success path exactly one writer of X lies and each such writer writes X exactly once (not inside a cycle, not a command taking a list input, for a process call `ref: X` stands as a single field in every one of its answers), or when all writers of X provably write the same record: every writer loads a record of X (any command except the root create; a child add loads its root), the root key of every writer comes from the same input place of the process (the flat input field of that name and type, or the property of the one non-list, one-token `accepts` field, also handed on into a sub-process), at least one of them works on a record that is already there (update, also in patch form; set; remove), and one of them lies on every success path (the answer reads the reference from that writer); otherwise it is a list (`list: true`). What is not provable stays a list: a loop, a partial way, a list input, a key read from a query result or from two input places, a node with several `consumedCalls` or with `reads`. A `ref` on something that is only read is a blocker. `ref` points at an aggregate root, child references stay with the command answer of an `identifier` node.
- **"Writes" comes from the call target (`V-PROC-ANSWER-2`):** own command (`dtoType`, own BC), foreign door of kind command (from the foreign door list), foreign process (its `answers` carry a `ref`), own sub-process (one of its ways writes). Never from `gives`, a field name or the `dtoType` of a foreign call. A foreign door list that cannot be loaded is a blocker "not verifiable", never "does not write".
- **One outcome name, one inner form (`V-PROC-OUTCOME-1`, replaces `V-PROC-ANSWER-4`):** two end nodes may carry the same `gives.name` only with an identical inner form (`kind`, per field `name, type, nullable, list, ref, rowsOf`; for `identifier` the key of the command answer); otherwise the second end node is a blocker. **Object form (`V-PROC-ANSWER-5`):** an end node gives `nothing`, `identifier` or `value` with `fields`; `gives: aggregate` and a scalar `value` are blockers. **At least one end node (`V-PROC-ANSWER-6`).**
- **Filter per world.** Inside (handler, `<Name>Context`, process nodes through `handle()`) every field of the end node is available. Outside, the one projection function leaves out each field whose `ref` points at an aggregate without a read door in the reader's world: a neighbour BC needs a read door at stance `domain` or wider (`{BC}Process::{name}()`, cross-BC call, `answers` of the door list), HTTP needs `outside` or wider (`routes.php`, OpenAPI). Fields without `ref` stay. A form emptied by the filter is the empty object form. A field that must stay outside needs a read door on the aggregate.
- **Door list of the owner:** a process door at stance `domain` or wider carries `answers` (one form per outcome — `outcome` is the `gives.name`, fields `{name, type, list, ref}`, outside view after the filter); a read door carries `key` (`{name, type}` of the public unique key, without key `id`). The caller of a foreign process reads only this list; "a foreign process writes" means at least one of its `answers` carries a `ref`.

The OpenAPI states the same: the key `x-jardis-response` of the operation is `fields` (or `reference` when every exit is the identifier of the same command). One outcome → `data` is a `$ref` on its component `{BC}{Process}{Outcome}`; several outcomes → `data` is a tagged union: `oneOf` over one named component per outcome with a `discriminator` (`propertyName: '@outcome'`, `mapping`). Every component carries `@type` and `@outcome` as constants. The caller switches on `@outcome`, never on which fields are present. The union is open: a new outcome is additive, an unknown `@outcome` is the error branch of the client, renaming or removing an outcome breaks the contract like a field rename. The declared answer is still a Process answer: 200, 4xx forms and the transaction bracket (Recipe 14) are unchanged. A node that must hand an earlier value to a later one declares it with `gives` and the later node reads it through the typed getter (`generated-code-workflow-api` §4).

**Recipe 7 — Bulk read: list → keys/ids → full aggregate records**

Every aggregate has a uniform read base (catalog: `generated-code-extend` §1), whose ways are doors with their own stance in `Doors.json`: WITHOUT a public unique key `get{Agg}ById` / `get{Agg}ByIds`, WITH one `get{Agg}By{UniqueKey}` / `get{Agg}By{PluralKey}` (e.g. `getOrderByOrderNumbers`) and NO ById/ByIds on the read facade (they stay internal, over the kernel seam, and have no row). With a key the auto-list items lead with that key column instead of `id` — so the recipe forks:

An aggregate **WITH** a unique key — list → keys → `get{Agg}By{PluralKey}`:

```php
$list  = $bc->order()->orderList($filter);                                             // filtered flat list: plain array {items, total, limit, offset}
$keys  = array_values(array_unique(array_column($list['items'], 'orderNumber')));
$records = $bc->order()->getOrderByOrderNumbers(new QueryOrderByOrderNumbers(orderNumbers: $keys))->getData()['items']; // list<OrderResponse> — objects: $records[0]->orderNumber, children ->; data = {@type: orderList, items}
```

An aggregate **WITHOUT** a unique key — list → ids → `get{Agg}ByIds`:

```php
$list  = $bc->heartbeatSignal()->heartbeatSignalList($filter);                               // filtered flat list
$ids   = array_values(array_unique(array_column($list['items'], 'id')));
$records = $bc->heartbeatSignal()->getHeartbeatSignalByIds(new QueryHeartbeatSignalByIds(ids: $ids))->getData()['items'];  // list<HeartbeatSignalResponse> — objects: $records[0]->serviceName, children ->; data = {@type: heartbeatSignalList, items}
```

Edge behaviour is plain IN semantics either way: empty input → `[]` · duplicates → one aggregate record · missing keys/ids → partial result without error · no order guarantee — match per key (or `id`), which every aggregate record carries. `get{Agg}ByIds` keeps being emitted family-internally regardless of a unique key — only the outward (public surface/OpenAPI) bulk-read surface and the list-item handle switch to the key when one exists.
