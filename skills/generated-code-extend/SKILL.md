### 0. DDD positioning

Jardis uses DDD vocabulary (BC, Aggregate, Domain Event, Repository, VO, Ubiquitous Language) under its own axioms — Closure-Orchestrator (`foundation-architecture` §3) and model-driven generation. See `foundation-architecture` § Positioning for the Functional-DDD stance this skill operates under.

| Rule | Consequence |
|---|---|
| **V11** — no business methods on entities | Behaviour lives in Actions and Domain Services, not on entities. Aggregate invariants are protected by the generated **pipeline**; cross-aggregate behaviour is authored as a **Process** (`{BC}/Process/`). |
| **V12** — responses are `DomainResponse` envelopes with an array payload | One serialisation surface across HTTP / CLI / queue. Typing is the transport adapter's job, not the domain's. The `data` array is flat at the root; inside a read answer the children are typed `{Child}Response` objects (`->`), which `json_encode` serialises like arrays. The generated `{Agg}/Command/Response/{Command}Response.php` classes do **not** change this: they are contract types describing the payload, never a handler return type. |
| **Call chains** | Aggregate reads (public surface): `$bc->{agg}()->get{Agg}ById\|ByIds\|By{Key}\|By{PluralKey}\|{agg}List(...)` (an aggregate WITH a public unique key carries `By{Key}`/`By{PluralKey}` and NO `ById`/`ByIds` on `{Agg}Read` — those two stay family-internal via the kernel seam; one without a key carries `ById`/`ByIds`) — the `{Agg}Read` facade is the call surface, no aggregate-root hop; an aggregate with no read door at `domain` or wider (every read row of its block `closed` in `Doors.json`) has no `{agg}()`/`{Agg}Read` at all and is reached only family-internally. Aggregate writes are **not** on the BC facade (G2) — the write facade `{Agg}` is reachable only family-internally, via the kernel seam: `$this->handle({Agg}::class)->{command}($dto)` (typically from a Process node body). BC-level processes (the other half of the public surface): `$bc->process()->{process}($dto)`. A command door at stance `domain` or wider (row of `Doors.json`) is a third entry of the public surface: `$bc->{command}($dto)` (incl. `$bc->create{Agg}($dto)`; Rules-Layer G10). A column declared `computed` in `Aggregate.json` is in no Create/Set/Add/Update command or request body; its one write path is the family-internal `$this->handle({Agg}::class)->set{Entity}Computed($dto)` (raises its own `{Agg}[{Fragment}]ComputedUpdated` event like every command, no outer door — `generated-code-recipes` Recipe 13). Taxonomy is discoverable; `handle()` / ClassVersion resolution anchors at each level. |

Upheld without compromise: aggregates are transaction boundaries with a single root; BCs are strict language boundaries (V6). The aggregate is **100 % generated** — you do not extend it in place. A Rich-Model instinct (custom validation, a VO, a domain service, coordinating two aggregates) is satisfied by **modelling a Process** in the Process Designer, never by editing the aggregate tree.

When Domain logic needs a Jardis runtime tool (cache, mail, queue, repository, HTTP client, …), look up the responsible package skill in §8 (Toolbox) before re-deriving the API.

### 1. Generated baseline — Platform-free hermetic layout

Facade chain: Domain → BC → **Aggregate Read facade** (`{Agg}Read`, reached via `$bc->{agg}()`) → query method — this is the BC facade's public surface, plus a parallel Domain → BC → Process facade → process chain (`$bc->process()`) and one direct method per command door at `domain` or wider (`$bc->{command}($dto)`, delegating into the command handler). The **Aggregate Write facade** (`{Agg}`, same directory) hosts the commands + `event()`; it sits behind the kernel seam (`handle()`/`context()`) and is reachable only from inside the Context family (classes extending the Domain Context) — never from the BC facade. Example: aggregate `Counter` in BC `Counter` in domain `MeterDevice`.

**Route convention of the public surface.** Every build also writes a machine-readable description of this same surface — one OpenAPI 3.1 document per domain at `Api/{Domain}/openapi.yaml`, a sibling of `App/` outside the PSR-4 tree. The routes it declares are the canonical HTTP shape of the public surface, and a transport layer (hand-written or generated) is expected to mount exactly these:

| Command / entry | Route |
|---|---|
| `Update{Agg}` | `PUT /{bc}/{aggs}/{identifier}` *(full replacement of the root scalars; `PATCH` stays free for a future partial-update concept)* |
| `Remove{Agg}` | `DELETE /{bc}/{aggs}/{identifier}` |
| `Add{Agg}{Child}` | `POST /{bc}/{aggs}/{identifier}/{children}` |
| `Remove{Agg}{Child}` | `DELETE /{bc}/{aggs}/{identifier}/{children}/{childKey}` |
| `Set{Something}` | `PUT /{bc}/{aggs}/{identifier}/{something}` |
| Process | `POST /{bc}/{name}` *(lcfirst of the process name — `processes/` no longer appears in the path; `operationId` is unchanged, still `{bc}_processes_{name}`)* |

**Exposing child commands.** Exposure is not limited to root commands: every aggregate command — root (`Update{Agg}`, `Remove{Agg}`) and child (`Add{Child}`, `Set{Entity}`, `Update{Entity}`, `Remove{Child}`) — opened on the BC facade by the stance of its row in `Doors.json` (block = the aggregate, row = the class name of the command, `closed` by default): at `domain` or wider it is the facade door `{lcfirst(Command)}({Cmd}DTO)` (e.g. `addGoodsReceiptLine()` on the generated `Purchasing` facade), at `outside` also a route and a right. A command door at `domain` or wider without a bound Rule only raises the warning `V-RULE-5` (its message says that process rules do not apply on this path). The key `bindings.{cmd}.expose` of `Closures.json` is retired (`V-DOOR-0`).

**Create is a door like every other.** The row is `Create{Agg}` (one name in every form: facade method `create{Agg}()`, handler `Create{Agg}`, guard `GuardCreate{Agg}`, right `{bc}.{agg}:create{Agg}`). At `domain` or wider it is the facade door `{BC}::create{Agg}({Agg}DTO)`; at `outside` it also has the route `POST /{bc}/{aggs}` (answer 201) and a right. A method name that collides with another facade method of the BC (also with `{agg}()`) is `V-QDEF-23` (blocker). A creation that needs more than the aggregate's own Create still runs through a Process — model one, open its row, and it appears as `POST /{bc}/{name}`.

**`Remove{Agg}{Child}` is not emitted for every child.** The table above gives the route *shape*; whether the command exists at all depends on the child. Two independent rules suppress the remove mutation of an `erm:one` child — and when either applies, there is **no** `Aggregate/Action/Remove{Child}.php`, **no** AggregateHandler method, **no** command and therefore **no** route:

| Case | Why |
|---|---|
| **DEPEND leaf whose depend-FK is NOT NULL** | removing it would null a mandatory column — the database would reject it |
| **`required` containment child** | there is no valid removed state |

A depend leaf whose FKs are all nullable keeps its remove mutation. `Remove{Agg}` (the root) is always emitted and is unaffected by this rule. So: if you expect a `remove{Child}()` on the write facade and it is missing, check the depend-FK's nullability first — that absence is the rule working, not a defect. Model the removal as a Process if the business really needs it (which then also has to say what replaces the mandatory reference).

Path parameters carry the **business identifier** wherever the aggregate or child has one; the internal id is a documented fallback only, and the build emits a warning when it has to fall back, so the gap stays visible. A door appears in the document only at the stance `outside` or wider (`Doors.json`; `domain` is facade only, `closed` nothing) — changing a stance moves it in and out of the document without touching a line of PHP. The document carries no `servers:` block: base URL and mount prefix are the surrounding app's business.

**`openapi.yaml` has a sibling artefact:** `Api/{Domain}/routes.php`, a hermetic `jardiscore/app` route-registration closure built from the same route table — how a transport layer wires it, decoding/dispatch/envelope details, and its `Api/{Domain}/` neighbourhood: `generated-code-wire-transport` §4 "Generated route registration".

**Notation:** aggregate code lives under `{BC}/Model/{Agg}/`; this skill abbreviates that directory as `{Agg}/`. Processes live one level up, under `{BC}/Process/` — a sibling of `{BC}/Model/`, **not** under any aggregate.

**The one rule:** The **entire** `{Agg}/` tree (`{BC}/Model/{Agg}/…`) is regenerated on every build (ForceOverwrite per file) — never edit anything inside it. (The collector segment is named `Model/`, not `Aggregate/`, renamed 2026-09-23; a BC-wide build cleans up a pre-existing `{BC}/Aggregate/` tree left over from before this rename, and dev-code imports of the old `…\Aggregate\{Agg}\…` namespace are rewritten to `…\Model\{Agg}\…` automatically by the merge.) There is **no `Platform/` segment**, in neither path nor namespace; the directory `{Agg}/` *is* the hermetic generator output. The directory hosts **two** facades: the write facade `{Agg}/{Agg}.php` (Commands + `event()`) and the read facade `{Agg}/{Agg}Read.php` (`get{Agg}ById`/`ByIds`/`By{Key}` + lists). Only the read facade is reached via the BC accessor `$bc->{agg}()` (the public surface, G2); the write facade is reached exclusively family-internally via the kernel seam, `$this->handle({Agg}::class)` — the same `protected` `handle()`/`context()` corridor every generated class in the Context family shares (code outside the Context family cannot call either method; PHP visibility enforces it at the type-system level, not just by convention). Hand code stands only at the places of the one table in §10 — never in the aggregate tree. The Generator emits the command-path segment: `Command/{Name}.php` DTO (`ForceOverwrite`), `Command/Handler/{Name}Handler.php` orchestrator (`ForceOverwrite`), `Command/Handler/Action/<NodeClass>.php` node stubs (`CreateIfNotExists` + `@node-id` body-preserve for custom and sub-process nodes), and event-data classes under `Event/` (`ForceOverwrite`, hermetic). Custom-node stubs are `CreateIfNotExists` with `@node-id` body-preserve, where your process logic lives. A versioned variant exists only for a stub class (node, Closure/Rule, Domain Service): it lives in a per-class `v{N}/` subdir resolved by ClassVersion (see `generated-code-versioning`); a hermetic class has none.

> **Note:** there is no `{Agg}/Api/` directory and no `Platform/` directory. The aggregate use-case API surface is split across two sibling facades in the same directory: the **write** facade `{Agg}/{Agg}.php` (FQN `<Domain>\<BC>\Model\<Agg>\<Agg>`, Commands + `event()`, family-internal via the kernel seam) and the **read** facade `{Agg}/{Agg}Read.php` (FQN `…\<Agg>\<Agg>Read`, Queries/lists, reached directly via `$bc->{agg}()` — the public surface). When BC and aggregate share a name, the BC facade imports the read facade under an alias `{Agg}AggregateRead` (e.g. `CounterAggregateRead`) to avoid a class-name collision with the BC's own class name; the accessor itself stays `{agg}()` either way (same pattern the write facade already used: `{Agg}Aggregate`). The Events registry lives under `{Agg}/Event/{Agg}Events.php`. **Processes** are BC-level (`{BC}/Process/{Name}/`, sibling of `{BC}/Model/`), reached via `$bc->process()->{process}()` through the hermetic `{BC}Process` facade. The process follows the same segment convention as the aggregate: Generator emits `Command/` (DTO + `Handler/` + `Handler/Action/`) and `Event/`; hand code stands only in the node bodies of `Handler/Action/` (§10).

**Vocabulary glossary** (binding for this skill set — the canonical term table; sibling skills point here):

| Term | Meaning |
|---|---|
| **Aggregate facade** (write) | `{Agg}/{Agg}.php` — Commands + `event()`; the aggregate is the write model (DDD). Family-internally reachable via the kernel seam, not via the BC facade. |
| **Read facade** `{Agg}Read` | `{Agg}/{Agg}Read.php` — one method per read door at `domain` or wider (`Doors.json`): `get{Agg}ById`/`ByIds` for an aggregate WITHOUT a public unique key, `By{Key}`/`By{PluralKey}` (no `ById`/`ByIds`) for one WITH it; `{agg}List` only if `Queries.json` declares it; declared queries of the root entity at `domain` or wider. Incl. `$version`, reachable via `$bc->{agg}()`. |
| **Public surface** | The public methods of the BC facade: `{agg}(): {Agg}Read` per aggregate + `process(): {BC}Process` + one direct method entry per **command door at `domain` or wider** (incl. `create{Agg}()`; Rules-Layer G10). No general write accessor. |
| **Kernel seam** | `handle()` / `context()` on `<Domain>Context` (the generated, hermetic base-class body — no package base class) — the family corridor through which all generated classes reach one another (incl. the aggregate write facade). `protected` — code outside the Context family cannot call `handle()`/`context()`; PHP visibility enforces it at the type-system level. |
| **Context family** / family-internal | Classes that extend `<Domain>Context` (aggregate facades, Process handlers, node actions, services, Rules, …) — they share the kernel seam among themselves. Code outside the family (transport layer, controllers) has no `handle()` access and must go through the public surface. |
| **Closure** | `{BC}/Closure/{Name}.php` — a `Closures.json` catalog entry (DeveloperOwned body), reusable across aggregates. Its signature follows the entry's declared contract: **0..n** named, typed `input[]` parameters (`command`/`aggregate`/`scalar`/`valuelist`, each optionally `optional`/a list) and one `output` — either the judgement type **verdict** (`RuleResult`) or a plain scalar from the closed column-type vocabulary. A **Rule** is simply the verdict-output case — in DDD vocabulary a **Specification**: input a subject, output `passed` or `rejected(reason)`. Callable exclusively via `$this->handle({Closure}::class)` (ClassVersion-capable, `Closure/v{N}/`) — never `new`. **Guard-bindable** (usable in `bindings.{Command}.chain`) requires additionally at most one `command` input **and** at most one `aggregate` input, no `scalar`/`valuelist` input (V-RULE-11) — the single-input `__invoke({Cmd}DTO): RuleResult` shape used throughout this section is exactly that bindable case, not the only signature the catalog allows; a freely composed Closure (e.g. a calculation with several scalar inputs) is equally valid but only reachable via `uses`, never via a Guard chain. Reads existing data only from its **own** BC (M9 prohibition: no foreign-BC import) — via its own read facade for facade-routed queries, or directly via the kernel seam (`$this->context({Handler}::class, $payload)()`) for a BC-internal read — the declared list with `limit: 1`, decided over `total` (see the Rule stub row below). |
| **`aggregate` input** | Carries the **aggregate entity** (`{Agg}\Model\{Agg}\Aggregate\Entity\{Agg}`) — the root plus its children through typed getters `get{Kind}()` (a list for `erm: many`) — never the read-facade DTO. The same type is in the stub parameter, the Guard `$root` and the Rule-node loader, so a Rule checks children it already holds instead of declaring a helper query (`reads`) for data that is loaded anyway; a body that uses only root getters runs unchanged. An example's `given.root` (for an input named `root`) carries the root fields plus the children under their relation names (nested objects / lists; V-RULE-22 reports an unknown key), and `ClosureTestCase::aggregate()` builds the entity from it; the work package lists the child getters in `types[].children`. At a Guard chain (a Command endpoint), the generated CommandHandler hands in the root it already loaded (`$handler->getData()`) — the Closure never loads it itself. A Create-Command has no root yet, so an `aggregate` input cannot bind to a Create-Command's chain (V-RULE-11). A Rule-node in a Process loads the root itself, through a generated, hermetic `{Agg}/Repository/Load{Agg}ForRule.php` closure — the same Query+Repository path the CommandHandler uses, never the read facade. When that lookup finds nothing, the node rejects (`NodeResult::reject`) with `RuleViolation` (422), a fixed `{lcfirst(bc)}.{lcfirst(agg)}.notFound` messageKey, `context: {identifier}` and no `rule` key (the rejection did not come from any catalog Closure's predicate). |
| **Guard** | `{BC}/Closure/Guard/Guard{Command}.php` (for the Create command `GuardCreate{Agg}.php`; a `Guard{Agg}.php` of an older build stays orphaned — delete it by hand) — generated, hermetic Chain-of-Responsibility Closure per bound endpoint: runs the configured Rule chain as AND with short-circuit. The generated CommandHandler only calls `$this->handle(Guard{Command}::class)($cmd)` — no Guard logic of its own. |
| **RuleViolation (422)** | Rejection status of a Rule (requires `jardiscore/kernel` ≥ v1.1.0) — payload `{rule, messageKey, context}`, stable across Rule versions. When the catalog entry declares a `messageKey`, the 422 carries exactly that key (set as a literal by the generated Guard and Process Rule node) — the `messageKey` passed to `RuleResult::reject()` is then not taken over; without a catalog key the body's key passes through. No exception path; the handler builds the 422 response directly. A Command door declares the `messageKey` of its 422 as a closed enum of the catalog keys of all Rules that can reject it (Rule-Sets resolved), as does a Process door while only Rules with catalog keys are reachable; the 422 stays open (plain `RuleViolation`, no enum) as soon as a reachable Rule has no catalog key or a dev body of the door's own BC is reachable, or a cross-BC call, external call or custom node with a foreign-BC call is reachable next to the Rules (its service body can answer 422 with its own key); a cross-BC or external call alone declares none. |

The seam is `protected` — hard at runtime **and** at the type-system level: code outside the Context family cannot call `handle()`/`context()` (PHP visibility error on a foreign call).

**Three file modes from the generator:**

- **ForceOverwrite** — rewritten on every build. The **entire** `{Agg}/` tree, Domain/BC facades, the hermetic `{BC}Process` facade, Process DTO (`Command/<Name>.php`) + orchestrator (`Command/Handler/<Name>Handler.php`) files, event-data classes (`Event/<EventClass>.php`), and the Rule-Layer hermetic Guard `{BC}/Closure/Guard/Guard<Command>.php` (the verdict class `RuleResult` is the package's `JardisSupport\Response\Data\RuleResult`, not generated). How to use it → `foundation-testing` §6.
- **CreateIfNotExists** — written once, then preserved. `Config/.env*` files; Process custom-node stubs `{BC}/Process/{Name}/Command/Handler/Action/<NodeClass>.php` (one file per node).
- **`@node-id` body-preserve** — Process custom nodes **and sub-process nodes**. On rebuild the developer body is preserved, keyed by the `@node-id` marker. Methods the developer changed and the developer's own methods always stay. An untouched generated helper method (anything but `__invoke`, which always stays) stays only while a kept method uses it — a call (`$this->`, `self::`, `static::`, also nullsafe) or its name inside a string literal (case-insensitive); a previously appended, unused helper disappears at the next build. For sub-process nodes: the first build emits a typed Dev-Stub (real Sub-input field names, the inner-door call, the `MapResponse` mapping with the inner events, open places for underivable values); subsequent builds preserve the developer body unchanged. (The Process-Designer "Force" build path can deliberately overwrite a node body instead.) **Rule stubs** (`{BC}/Closure/<RuleName>.php`) use a related but distinct, per-method merge rule (no `@node-id` — a Rule has no single declaring node): an **untouched** generated method migrates wholesale to the new signature/body, a **hand-edited** method is kept 100% verbatim (including its docblock) — for every generated method on a DeveloperOwned class, not just `__invoke`.

**Aggregate facade mechanics.** The aggregate's public surface for reads (absent for an aggregate with no read door at `domain` or wider — no `{Agg}Read`, no route; commands and queries stay usable through the kernel seam and from processes) is `{Agg}/{Agg}Read.php` (`extends <Domain>Context`), reached via `$bc->{agg}()` → `handle(<Agg>Read::class)` — the BC facade's public surface (G2), public FQN `<Domain>\<BC>\Model\<Agg>\<Agg>Read`. The write facade `{Agg}/{Agg}.php` (public FQN `<Domain>\<BC>\Model\<Agg>\<Agg>`) hosts the commands + `event()` and is reached only family-internally via the kernel seam, `$this->handle(<Agg>::class)` — never through `$bc->{agg}()`. Both facades are fully regenerated (ForceOverwrite) — there is no body-merge, no `@flow-id`. You never add methods to either; new aggregate behaviour is modelled in the Designer (structure) or authored as a Process (behaviour). ClassVersion resolves a versioned variant `<Domain>\<BC>\Model\<Agg>\v{N}\<Agg>` (write) or `…\v{N}\<Agg>Read` (read) when the per-call `$version` argument is non-empty (see `generated-code-versioning`).

**Read base — the read ways of an aggregate (hermetic, emitted on every build; the stance of each way is its row in `Doors.json`, default `outside`, and only a way at `domain` or wider is a method of `{Agg}Read`).** Without a public unique key the ways are `ById`/`ByIds`, with one `By<Key>`/`By<PluralKey>` only — `ById`/`ByIds` then stay internal (kernel seam) and have no row:

| Method | Query DTO | Response data block |
|---|---|---|
| `get<Agg>ById($q)` | `Query\<Agg>ById { id }` — type follows the PK | `['@type' => '<agg>'] + <root fields flat>`, children `{Child}Response` objects; nothing found → `[]` |
| `get<Agg>ByIds($q)` | `Query\<Agg>ByIds { ids }` — `list<PK type>` | `['@type' => '<agg>List', 'items' => list<{Agg}Response>]` — objects, **no `[0]` collapse** |
| `get<Agg>By<UniqueKey>($q)` | `Query\<Agg>By<Key> { <keyField> }` — camelCase column, no entity prefix | `['@type' => '<agg>'] + <root fields flat>`, children `{Child}Response` objects; nothing found → `[]` |

**Reading the data block in PHP.** Only the root level is spread into the array: `getData()['counterNumber']` is correct for a root field, but every child is a typed `{Child}Response` object (a list of them for `many`) — `getData()['registerRelation'][0]->register->obis`, never `…[0]['register']` (an array access on an object throws at runtime; PHPStan does not see it, `getData()` is `array<string, mixed>`). The `items` of a bulk read are `{Agg}Response` objects as well (`$item->counterNumber`). The flat `<agg>List` is the exception: its `items` stay plain arrays (`$list['items'][0]['id']`). Shape reference: `generated-code-recipes` Recipe 6.

`By<UniqueKey>` exists exactly once per aggregate — the identifier chain picks the unique business key (e.g. `getCounterByIdentifier(new QueryCounterByIdentifier(identifier: $i))`); an aggregate without a unique key gets only ById/ByIds on its read facade. An aggregate WITH a unique key gets `By<UniqueKey>` and the bulk variant `By<PluralKey>` (e.g. `getOrderByOrderNumbers`) INSTEAD of ById/ByIds (see Bulk-read recipe below). Further `get<Agg>By<Custom>` methods come from queries DECLARED in the BC's `Queries.json` (`Source.json` has no `queries:` text path — a leftover one is rejected, `V-QDEF-23`); `<agg>List(<Agg>ListFilter)` is the flat list — **not** part of the uniform read base above: it is an ordinary DECLARED query in the BC's `Queries.json` (the base list, seeded there once when an aggregate is first saved), so an aggregate whose `Queries.json` carries no such query has no `<agg>List` method. A suffix-less `get<Agg>` does not exist. The ids are the **internal**, family-wide handle of the domain API (the ById/ByIds query classes and handlers keep being emitted regardless of a unique key and are reached over the kernel seam; only without a unique key are they also read doors) — the facade is no public REST surface; exposure is the surrounding app's decision — and FK/child internals stay encapsulated either way.

**Tenant and user markers (`tenant` / `user` on the aggregate entity).** For an entity with a `tenant` or `user` marker, the Query and Command DTOs that address or write it do not carry the marked column as client input; the tenant is the first constructor argument of the generated `{Query}Filter` (no default), so a read over the kernel seam without the scope is a type error. The generated `routes.php` fills `tenant`/`user` from the request attributes (`RequestAttribute::TENANT` / `::SUBJECT_ID`, `jardissupport/contracts` >= 2.17) and puts the per-route middleware `RequireRight` (right of the endpoint, `jardiscore/app` >= 3.2) and `RequireRequestAttribute` in front: a missing right or attribute answers 403 before the handler, never 500. Hand code reads tenant and user from the process DTO (`$ctx->input()->tenant` / `->user`, filled by the door) and passes them on explicitly, never from client input. A `tenant` marker filters every read variant of the root, and a child entity whose column `adopt`s the effective tenant column of an ancestor is filtered by derivation (every query rooted at it gets the tenant filter, the value comes from `adopt`); a `user` column is only a write value. The write answer and a 404 context carry only the key, not the scope. A `writeOnly` column is absent from every Read DTO, public list item, event payload and command answer. A hand-written family-internal check (verify a stored digest) reads it through a declared query that stays `closed` or `domain` (no `Doors.json` row at `outside`), called over the kernel seam (`$this->context({Handler}::class, $filter)()`); the generated internal query handler projects the column, no outer form ever does.

> **DTO class names vs. alias.** The read/write DTOs are really named **`<Agg>`** (Command, e.g. `Counter`) and **`<Agg>ById` / `<Agg>ByIds` / `<Agg>By<Key>`** (Query, e.g. `CounterById`) in their own `Command\` / `Query\` namespaces. The `Command…` / `Query…` prefix used throughout this skill (e.g. `CommandCounter`, `QueryCounterById`, `QueryCounterByIds`) is a **`use … as …` alias defined inside the aggregate's write facade** (Command) **or read facade** (Query), not the real class name. Code **outside** either facade must import the real name (`use …\Query\CounterById;`) or add its own `as` alias.

**Bulk-read recipe** (the recipe forks on whether the aggregate has a public unique key):

An aggregate **WITHOUT** a unique key: list items lead with the root id, so the set pattern is:

```php
$list    = $bc->heartbeatSignal()->heartbeatSignalList($filter);
$ids     = array_values(array_unique(array_column($list['items'], 'id')));
$records = $bc->heartbeatSignal()->getHeartbeatSignalByIds(new QueryHeartbeatSignalByIds(ids: $ids))->getData()['items'];   // list<HeartbeatSignalResponse> objects
// match per id (`$record->id`) — every aggregate record carries it
```

An aggregate **WITH** a unique key: the list SELECT leads with that key column instead of `id`, and the bulk read goes through the `By<PluralKey>` variant:

```php
$list    = $bc->order()->orderList($filter);
$keys    = array_values(array_unique(array_column($list['items'], 'orderNumber')));
$records = $bc->order()->getOrderByOrderNumbers(new QueryOrderByOrderNumbers(orderNumbers: $keys))->getData()['items'];   // list<OrderResponse> objects
// match per orderNumber (`$record->orderNumber`) — every aggregate record carries it
```

Edge behaviour (existing infrastructure semantics, nothing new underneath): empty input → empty list · duplicates → deduped (IN semantics) · missing keys/ids → partial result, no error (consistent with ById/By<Key> → `null`) · no order guarantee. Family-internal callers (kernel seam) can still use the ById/ByIds handlers either way — the read facade, the list-item handle and the public surface (OpenAPI) are key-only when a unique key exists.

**Process facade mechanics.** `{BC}/Process/{BC}Process.php` (`extends <Domain>Context`) is hermetic — fully regenerated on every build (`ForceOverwrite`, no body merge, no `@process-id`). It carries one thin-dispatch method per process; the process logic lives in the orchestrator's custom-node bodies under `{BC}/Process/{Name}/Command/Handler/Action/`. **Process stance:** a process whose row in the block `process` of `Doors.json` is `closed` is a pure sub-process of its own BC — the facade emits **no method** for it (it is only reachable as a sub-process node inside another process of the same BC). `domain` gives the facade method (also for the other BCs of the domain), `outside` adds route and right, `open` a route without login and right (default `outside`). The stance controls only the doors; the process DTO, orchestrator, and node stubs are always generated. A sub-process node or Cross-BC-Call onto a FOREIGN door needs the stance `domain` or wider there (`V-CONSUMED-EXISTS`, blocker). The stance is set in the door table of the BC page or with `save_doors`; the keys `subprocessOnly` and `visibility` are retired (`V-DOOR-0`).

**BC facade caches nothing** (each `->{agg}()` / `->process()` / `->{command}()` is a fresh `handle()` resolve). **All facades** delegate through `context()` / `handle()`. **Never** instantiate handlers directly (V2/V3).

### 2. Where customization goes — the aggregate has no edit slot

The aggregate tree is hermetic; **nothing** under `{Agg}/` is a developer override point. There are exactly four sanctioned ways to change behaviour:

| You want to… | Do this |
|---|---|
| Add or change **behaviour** (validation, calculation, cross-aggregate coordination, event transport, external calls) | Model a **Process** in the Process Designer. Generator emits the DTO + orchestrator + node skeleton under `{BC}/Process/{Name}/Command/` and `Command/Handler/Action/` (plus `Event/` for event nodes), and a thin-dispatch method on the hermetic `{BC}Process` facade (`$bc->process()`). Your logic lives in the custom-node bodies (`@node-id` preserve); further hand code exists only at the places of §10. A process has **no aggregate ownership** and may coordinate several aggregates. |
| Change the aggregate's **structure / invariants** (entities, relations, keys, `required`/`depend` rules, commands/queries) | Re-model the aggregate in the Aggregate Designer (`Aggregate.json`) and rebuild. The generated tree changes accordingly. |
| Provide a **versioned variant** of a stub class (node, Closure/Rule, Domain Service; tenant / feature-flag) | Put the variant in a `v{N}/` subdir next to the stub (`Action/v{N}/<Node>.php`, `Closure/v{N}/<Name>.php`, `Service/v{N}/<Name>.php`) and select it **per call** via the `$version` argument threaded through every facade method — there is no domain-wide default (the Domain facade is `final`, `{Domain}Context` hermetic). ClassVersion (`LoadClassFromSubDirectory`) resolves `…\v{N}\<Class>` before the baseline. A hermetic class (anything under `Model/{Agg}/`, a handler, a facade) takes no variant: add behaviour in a Process or re-model instead. **Note:** a versioned build (`version: "v2"` on `build`/`build_process`/`build_domain`, CLI `--version`) writes the fresh `final` stub frame of each stub class into its `v{N}/` subdir (same signature, namespace `…\v{N}`, no `extends`; the body you write survives rebuilds) — never a hermetic class. See `generated-code-versioning`. |
| Guard a Command with a **business rule / existing-data check** before it runs (Rules-Layer) | Declare a catalog entry + endpoint binding in `Closures.json` (BC-level, sibling of Process/Steckbrief). Generator emits a Rule stub under `{BC}/Closure/{RuleName}.php` (guard-bindable shape: `__invoke({Cmd}DTO): RuleResult` — one of several signatures the general Closure contract allows, §1 "Vocabulary glossary") plus a hermetic Guard closure that runs the bound chain (AND, short-circuit) ahead of the Command. Your logic lives in the Rule stub body — existing-data checks stay within your **own BC** (M9), via the read facade or directly via the kernel seam (`context()`) for a BC-internal read; anything needing a cross-BC read or a multi-step/side-effecting flow is process territory, not a Rule. **Until you implement it, the stub throws** (500), it does not fail open — see the Rule stub row in §1 and `generated-code-recipes` §3 Troubleshooting. |

**Migration note (path collision).** In the pre-Platform-removal layout a file directly under `{Agg}/Command/…` was a **shadow override** that the ClassVersion reader (`segmentNames: ['', 'Platform']`) found *before* the generator class under `{Agg}/Platform/Command/…`. The Generator writes to `{Agg}/Command/…` itself (ForceOverwrite) — an old baseline override at that path **collides** and is overwritten. There is no auto-migration. To migrate such an override: move the behaviour into a Process (`{BC}/Process/`), or re-model in the Designer. The build deletes the orphan `{Agg}/Platform/` directory on regen.

**Domain support code.** There is no place for value-object or helper classes: a value is checked by the model (column type, value list, process input type, Validator) or by a Closure/Rule; a Domain Service lives at `{BC}/Service/{Name}.php`, the one location of §10 — the rule fixes the place, nobody chooses it by convention. The Generator owns `Command/`, `Command/Handler/`, `Command/Handler/Action/`, and `Event/` of a process; hand code in it stands only in the node bodies of `Action/`. A directory directly under `{BC}/Process/` that is not a process of the model and holds no generated node file (no `@node-id` marker) is **not deleted** — the build warns about it with its path in the build result; it is a stray, no hand-code place. An orphaned, generator-created process directory (the process was removed from the model) is deleted **with its whole content**, developer code included.

**Generated Service stubs sit at one place.** The Service stub of a Cross-BC-Call or External-Call node is `{BC}/Service/<Name>.php` of the calling BC — you choose only the business service name (or leave it to the target-derived default), never a directory or a tier. A developer body an earlier build left at an old place moves to `{BC}/Service/` with the next build. See §1 for the write mode (header-aware merge).

**FieldMap + Entity Validators are generated** (`{BC}/FieldMap.php`, `{BC}/Entity/Validation/<Entity>Validator.php`, ForceOverwrite) — both are **BC-level** (BC-rooted, one per BC table over all BC tables), not aggregate-scoped. The FieldMap exposes one `{table}Columns()` write-map method per BC table. Logic that must participate in those generated entry points belongs in a **Process node** that runs before/after the aggregate call — never as an in-place edit of the FieldMap or validator.

**Validators for "absent" (rule).** A developer-written validator that reports an absent value must implement `JardisSupport\Contract\Validation\MissingValueValidatorInterface` (jardissupport/contracts ≥ 2.3.0); the generated `ValidationException` takes `fields[].reason` from the validator kind (validation ≥ 1.2.0), so only this marker yields `missing` — wording of the message is irrelevant, a finding without a kind is `invalid`.

**Bulk-read warning.** Every generated collection query handler (`get{Agg}ByIds`, `get{Agg}By{Key}s`) logs one warning through the Kernel logger when called with more than 100 keys (`BULK_WARN_ABOVE`); it never aborts — chunk large key lists in the caller.

**Rename & rebuild (object rename).** Domain, BC, aggregate, and process can be renamed in the Designer **even after a build exists**. A rename updates the definition and all referencing JSON documents immediately (`subProcess`, `consumedCalls` — cross-BC included, `accepts`), stamps the renamed artefact and every affected consumer "rebuild needed", and leaves a rename trace; the **next build** pulls the code along. What that means for your code:

- **Developer code survives every rename.** Dev-code-bearing process trees are **moved** (not deleted + regenerated): file **bodies** stay byte-identical; only the mechanical header (`namespace` line + `use` lines pointing at renamed generated namespaces) is patched — PSR-4 stays intact, PHPStan stays green. Hermetic trees (aggregate) are simply regenerated under the new name and the old tree is cleaned up. `v{N}/` directories move physically with the tree (no version-specific namespace follow-up yet).
- **Consumers show a reason note.** A consumer process whose `consumedCalls`/`subProcess` reference was rewritten carries a persisted note (old → new, affected calls), visible in its detail panel; a successful build of that consumer clears note + stamp.
- **Hand code outside the output tree is NOT rewritten.** App/bootstrap wiring or external event listeners that mention renamed FQCNs by hand get a naming warning in the rename preview — updating them is your job.
- **Node rename** (Ticket panel) keeps the `@node-id` body across the file rename; event-mode nodes get their `Event/` class swept along.
- **Node class names are PascalCase, derived from the model name.** The generator derives ONE class name per node: `ucfirst(name)` (an Event ◇ node `mode: async`: node class `ucfirst(name)` + `Node`, event-data class `ucfirst(name)`). File, class and FQCN of node **and** event all come from that one derivation — a model name `checkStock` yields `CheckStock.php` / `final class CheckStock` (PSR-12). Write node names in PascalCase; a lowercase name still builds but the validator warns `V-PROC-NAME-CASE` and names the derived class. A project built before this rule (`checkStock.php`, `Event/stockChecked.php`) migrates on its **next build**: the node file is renamed by its `@node-id` marker with the developer body byte-identical and the old file removed, the event data class is rewritten under the new name — and **every rename is reported as a build Hinweis** (`Knoten <id>: checkStock.php → CheckStock.php, Body übernommen`; for an Event `… FQCN geändert: Listener-Importe prüfen`). The event FQCN changes with it: **hand-written listeners/imports of `…\Event\stockChecked` are yours to update** (they sit outside the output tree and are not rewritten).
- Renaming back (new → old) is a normal rename with the same rules; a rename preview (impact list incl. foreign-BC consumers and dev-surface hints) runs before every level rename in the UI.

**A Closure/Rule catalog-entry rename does NOT follow the rule above — your stub is not moved.** Renaming a `Closures.json` entry (Closure-Editor or MCP `rename_closure`) rewrites the JSON catalog key, every binding chain naming it, every other Closure's `uses` (Set member or free reference alike), and every process Rule-node's `rule` field — but the **developer-owned stub file itself stays where it is**, under its old class name; the rename response carries an explicit warning ("generated dev stub … was not moved — rename it by hand, or let the next build regenerate a fresh one under the new name"). Move your `__invoke()` body yourself, or accept a freshly generated (unimplemented, throwing) stub at the new path. Deleting a Closure still bound to ≥1 chain, referenced by ≥1 `uses`, or used by ≥1 process Rule-node is blocked with `409 IN_USE` and the list of referencing bindings/processes/sets; `force=true` deletes anyway and leaves those references dangling.

| V2 | No `new` for Services / VOs / Entities — only `Exception`, `RuntimeException`, `DateTimeImmutable`, `DateTime` |

| V7 | No traits, no `abstract` (except Exception hierarchies) |

| V11 | No business methods on Entities |

That class is a **contract type**, published so a client can be typed against the write door; it is **not** a return type. The handler signature stays `DomainResponseInterface`, its payload stays the array, and nothing about the dispatch changes — **do not rewrite a handler to return one of these classes.** They are hermetic like the rest of the tree (never edit), and derived from the same source the handler body is rendered from, so they cannot drift from what the handler actually writes. |
| V13 | A Rule (`{BC}/Closure/{Name}.php`) reads existing data only from its **own BC** — via that BC's read facade (`$this->handle({BC}::class)->{agg}()`) for a query at `domain` or wider, or directly via the kernel seam (`$this->context({Handler}::class, $payload)()`) for a BC-internal read such as a list read with `limit: 1` — no foreign-BC import, no cross-BC read from inside a Rule (M9). Enforced by convention + a stub docblock nudge, not yet by static analysis. A cross-BC existing-data check belongs in a Process, not a Rule. |

Hand code stands only at the places of §10: node bodies under `{BC}/Process/{Name}/Command/Handler/Action/`, Closure/Rule bodies, Domain Services under `{BC}/Service/`, and `App/**` delivery code. There is no aggregate-root file to extend, no `{Agg}/Api/` registry, and no `Platform/` directory. The aggregate's two facades host the inline registries of generated Commands (write facade, family-internal via the kernel seam) and Queries/lists (read facade, reached via `$bc->{agg}()`, the BC facade's public surface); BC-level operations route through the `{BC}Process` facade via `$bc->process()`.

### 7. Constructing `DomainResponse`

The payload of a response is **flat**: the data is the business object itself and names its type in the field `@type` — no handler-name level, no root-key level around it (the package's `TransformResponse` takes the data of the one root context as `data`; two contexts carrying data throw a `LogicException`, nothing is merged silently). A Process node body does **not** construct the response: it returns a `NodeResult` and the door builds the `DomainResponse` (`generated-code-workflow-api` §4/§6):

```php
public function __invoke(MyContext $ctx): NodeResult
{
    $found = $this->read(GetCounterListHandler::class, new CounterListFilter(identifier: $ctx->input()->identifier, limit: 1))->first();

    return $found === null
        ? NodeResult::reject(ResponseStatus::NotFound, 'counter.notFound', ['identifier' => $ctx->input()->identifier])   // 4xx ends the run; the door forms the typed failure
        : NodeResult::ok(['@type' => 'counter', 'counterIdentifier' => $ctx->input()->identifier]);                  // reference value, flat
}
```

The `$this->result()` helpers below belong to the generated handlers and the door, which build the response through them; a node body never calls them.

| Status | Use |
|---|---|
| `Success` (200) | Read with data; also **every successful write over the wire** — a Process answers 200 with the reference value (or the data it declares via `successOutput`, `generated-code-recipes` Recipe 6; the reference value is the public key outside, `id` only without a key — inside the BC the command answer also carries the root `id`), never 201 (`ResponseStatus::Created` appears only inside the generated aggregate Create handler, which is family-internal and never a route) |
| `NoContent` (204) | Write succeeded, empty body |
| `ValidationError` (400) | DTO / invariant validation failed — thrown as a dedicated `ValidationException` in generated Validate classes (typed property `fields`: `list<array{field, reason, message, messageKey}>`; `field` = outer name per FieldMap as dot path with the list index at every door (`orderItem[0].qty`), `reason` = `missing` only for a validator marked `MissingValueValidatorInterface` (absent enum/date/number/boolean/value-list/child), else `invalid` — an empty string or `null` in a NOT-NULL string column is `invalid`; a body key the contract does not name answers `unknown` from the door, before the handler), caught **before** the catch-all `\Throwable`; precedes Rule evaluation (form before business). Payload `{"@type":"validation","fields":[…]}` |
| `RuleViolation` (422, Rules-Layer; requires `jardiscore/kernel` ≥ 1.1.0) | A bound Rule chain rejected the Command — built directly by the generated Guard-calling handler code, **never thrown**; at a Process door the 422 may also come from a dev body of the own BC (open `messageKey`, see the contract note above); `messageKey` is the catalog key when declared, not the body's `reject()` argument; payload `{"@type":"ruleViolation","rule","messageKey","context"}` (stable across Rule versions, `messageKey` = the catalog key when the entry declares one, i18n resolved by the surrounding app; an empty `context` is an empty object). A **technical** failure inside a Rule's existing-data check (DB down, timeout) is never a 422 — it falls through to 500. |
| `Unauthorized` / `Forbidden` (401/403) | Raised by middleware, not here |
| `NotFound` (404) | Target absent — payload `{"@type":"notFound","context"}` (`context` = the identifier(s) that failed to load, an object) |
| `Conflict` (409) | A write lost its read basis (stale write/delete) — payload `{"@type":"concurrencyConflict","reason","aggregate","context"}`; the handler catches the conflict exception before the catch-all `\Throwable`; a transient database conflict (typed `TransientConflictException`, contracts ≥ v2.6.0 / repository ≥ v1.6.0) is a 409 `stale_write`/`stale_delete` too, not a 500 — on MariaDB/MySQL inside a process it surfaces at the process bracket, not at the node (`generated-code-recipes` Recipe 11 Case B); repeat = client retry in a new transaction |
| `InternalError` (500) | Unexpected `Throwable`; the message is in `errors` |

**409 `violated` and `expected`.** A `duplicate` 409 carries `violated: list<string>` (outer field names of the hit unique columns, child fields as `<kindProperty>.<field>`; `[]` for unknown columns and for every `stale_write` / `stale_delete`) — see `generated-code-recipes` Recipe 12. The aggregate **write facade** `{Agg}` (family-internal, reached via the kernel seam / `$this->context(...)`) takes an optional `array $expected = []` after `string $version` on the root writers (`update{Root}`, `set{Root}Computed`): outer field name ⇒ the value the calling node read; the handler uses it as the CAS expectation instead of the freshly loaded state (`generated-code-recipes` Recipe 11, Case B). It is **not** part of the BC facade, the Rules door, routes, OpenAPI or any Command DTO; child writers and `Remove` do not carry it; an unknown key answers 500.

When you build a 400/404/409/422 by hand, use exactly these typed payloads — the same four forms every route, aggregate command and Process answers with. A dev body refuses with `NodeResult::reject(status, messageKey, context, errors)`; the package builds the form from the context keys it knows (400 `fields`, 409 `reason`/`aggregate`/`violated`, 422 `rule`; the rest is the form's `context`), a Process 4xx without a form (401/403/405) is passed through unchanged. The `messageKey` a node declares with `rejects(status, key)` (else the one named in `reject(...)`) is set on `data` after forming, for every 4xx status (also when it is not a field of the form, and also for a 4xx that has no form).

**Status staircase (Rules-Layer):** `400` (field validation) → Load → `404` (root not found) → `422` (business, Rule chain) → `404` (child / apply miss, after the Guard) → `409` (persist conflict) → `500` (technical) — a Command dispatch checks field validation first (cheap, local), then the Rule chain (potentially DB-bound), so a malformed request never pays for a existing-data check it can't pass anyway. A Process node calling a Command translates this deterministically through `MapResponse`: 2xx → `ok(data)`; a 4xx (including `422`) → a `reject` with the same status — the run ends, the engine routes no reject; `5xx → the exception path` (500, cause logged) — never a blanket `isSuccess() ? ok : route(OnFalse)` mapping, which cannot tell the two apart. Only a Dev decision inside a node may map a 4xx to a route.

**Process gate (before the first node).** A Process rejects a faulty command input before any node runs and before its transaction opens: the orchestrator `{Process}Handler::__invoke` starts with a private `rejectInvalidInput()` that checks every command input field (single value, list, union) with the same `Validate{Command}` the aggregate's own handler runs (one multi-catch over the validation exceptions of all accepted commands; a Remove has no Validate and is not checked). A field error answers 400 `validation` with `fields[]` in the gate's path form (`<property>.<field>`, `<property>[<i>].<field>`) at every door (route, `process()` facade, sub-process), so not even a 422 Rule node or a writing predecessor node comes first. The 400 lists one finding per field with `messageKey` `validation.missing` / `validation.invalid` (the package adds it from the finding's `reason`; a text the validator delivered stays untouched).

**TOCTOU boundary (v1, known limitation).** A Rule's existing-data check and the Command's subsequent Apply/persist are two separate steps — nothing in the generated Guard or CommandHandler locks between them. A concurrent write between the Rule's read and the Command's write can pass a Rule that would have rejected the now-changed state (time-of-check-to-time-of-use). This is a deliberate v1 boundary, not a bug: close it in the model — as a hard invariant in the DB schema (`UNIQUE`, `CHECK`, FK) that fails the write outright rather than relying on the Rule alone (`generated-code-recipes` Recipe 12), or as state with a conditional write (Recipe 11). A recheck of your own is not a Jardis artefact and has no place in a Rule body. A general recheck/optimistic-locking mechanism is not yet part of the generated code — that is a gap to build in Jardis or to report (§10), not to emulate.

`$this->result()` helpers:

- `setData(array)` — replace the flat payload (last writer wins; carry `@type`)
- `addData(string $key, mixed $value)` — additive field of the flat payload
- `addError(string $message)` — accumulates under the context name → on the wire `errors` is an object `{<context>: [message, …]}` (`{}` when empty, never `[]`) — use it for technical messages (a 500); the cause of a typed 4xx belongs in the form's `data` fields (`fields[]` / `context` / `rule`+`messageKey`), not in `errors`
- `addEvent(object $event, EventScope $scope = EventScope::Internal)` — accumulates only; the handler does **not** dispatch. Generated aggregate life-cycle events are `EventScope::Internal`. Publication is the **caller's** job after commit: a custom Process node that holds the command's response hands its events to a transport, or an Event ◇ node announces a Domain event with `NodeResult::route(Route::OnTrue)->withEvents(...)` — the events travel with the result, the handler collects those of a successful run as `EventScope::Domain` on the process response (see `generated-code-recipes` §1). `getEvents(?EventScope $scope = null)` filters by scope; with no argument it returns all scopes. `EventScope` is a `jardissupport/contracts` enum.

`DomainResponse`/`ContextResponse` (the Response pair), `TransformResponse` (the envelope mapper) and `BuildResponseData` (how a Process answer becomes the envelope's `data`) are **package classes of `jardissupport/response`** (`JardisSupport\Response\Data\Response\`, `JardisSupport\Response\Handler\Response\`; skill `support-response`) — the generated `{Domain}Context` only reaches them through `result()` / `transformer()`. The clock of a run is PSR-20: `{Domain}Context::clock()` resolves `SystemClock` through the kernel seam, and it stamps the envelope and the columns marked `auto: created|modified` in `Schema.json` (read ONCE per write); a test or a deployment substitutes it through the container key `CLOSURE_STAND_INS` (`{Domain}Context::CLOSURE_STAND_INS`, a map `className => stand-in`, e.g. a `FixedClock` under `SystemClock`). The `DomainResponseInterface`/`ContextResponseInterface` contracts, the `ResponseStatus` enum, and `EventScope` live in `jardissupport/contracts` (no dedicated dev-skill).

**The context head of a stub (PHPDoc chain).** Business meaning is description (Domain → BC → Process → Node) and lands as PHPDoc, the context the AI reads where it implements. The Domain description stands at `<Domain>.php`, the BC description at `{BC}/{BC}.php`, the process description at `{P}Handler` (rows 1, 2, 4); every stub of rows 5, 6 and 8 carries the chain as the last block of its class docblock — generated frame, so every build refreshes it and the hand-written body is never touched:

```
 * Kontext-Kette (von oben nach unten):
 * Domain: <Name>
 *     <description of the Domain, indented, may span lines>
 * BC: <Name>
 *     <description of the BC>
 * Prozess: <Name>            (node stubs only)
 *     <description of the process>
 * Knoten: <Class>            (Closure: / Service: for a stub without a process)
```

A level line is `<Level>: <Name>` at the start of a docblock line and carries the name only; description lines are indented, an empty description leaves the level line without text (the registry warns `V-DESC-EMPTY` for an empty Domain, BC or process description). The node, Closure or Service's own description is the prose above the chain. The Gesetz-Gate (invariant D, `StubChainRule`) checks the level lines — a node stub needs Domain, BC, Prozess, Knoten; a Closure stub Domain, BC, Closure; a Domain Service stub Domain, BC, Service — never the text.

**If the model cannot express it,** no hand-code place opens up: a missing capability is a gap in Jardis. When you work on Jardis itself, build it in the package or the generator first and use it afterwards; when you work on an app, report it as an issue and wait. A substitute in the project — an interim, a workaround, a class in a place that is not in the table — is a violation, not progress.

**Removed hand-code places** (a file there is a violation; the generator emits no new ones):

1. `{Domain}/Service/*` (the Cross-BC-Call stub always, External-Call `level: domain`) → `{BC}/Service/` of the calling BC.
2. `{BC}/Process/{P}/Service/` (External-Call `level: process`, formerly the default) → `{BC}/Service/`; the External-Call field `level` is retired.
3. `{BC}/Process/{P}/Query/` and `Repository/` → none: reading is a declared Query, writing is an aggregate Command or a `process()` call.
4. `{BC}/Process/{P}/ValueObject/` and free projector or helper classes → none.
5. `v{N}/` variants of hermetic classes → none; `v{N}/` exists only for rows 5, 6 and 8. `App/**` is the delivery place of row 10; a process trigger by event or time is a project of its own, not a hand-code place.

The generator emits none of these places any more; a developer body left there moves to `{BC}/Service/` with the next build (Hinweis per move).

### 11. The way

The order of work for a change to a Jardis domain. Each step has one skill; do not skip ahead.

1. **Model.** Express the change in the model first (schema, aggregate, process, queries, closures), through the authoring doors. → `design-headless-mcp`, `design-draft-schema`.
2. **Check.** Validate the model before building; fix findings in the model, never in the output. → `design-headless-mcp` (the `validate_*` tools).
3. **Build.** Generate the code; the hermetic tree is overwritten on every build (§2). → `design-headless-mcp`.
4. **Hand code.** Fill the stubs the build produced — node bodies, Closure/Rule bodies, `{BC}/Service/` — at the places of §10, using only Jardis artefacts. What the model cannot express is a missing Jardis capability: build it in the package or generator (when working on Jardis itself) or report it as an issue (when working on an app), then wait — no substitute in the project. → this skill, §5 and §6; recipes in `generated-code-recipes`.
5. **Tests.** Test behaviour through the doors, with the generated scaffold. → `foundation-testing` §6.
6. **QA.** Run the gates of the project profile, model checks first, then the gates. → `process-run-stage` §7.
