### 7. Constructing `DomainResponse`

The payload of a response is **flat**: the data is the business object itself and names its type in the field `@type` — no handler-name level, no root-key level around it (the package's `TransformResponse` takes the data of the one root context as `data`; two contexts carrying data throw a `LogicException`, nothing is merged silently). A Process node body does **not** construct the response: it returns a `NodeResult` and the door builds the `DomainResponse` (`generated-code-workflow-api` §4/§6):

```php
public function __invoke(MyContext $ctx): NodeResult
{
    $found = $this->read(GetCounterListHandler::class, $this->handle(CounterListFilter::class, identifier: $ctx->input()->identifier, limit: 1))->first();

    return $found === null
        ? NodeResult::reject(ResponseStatus::NotFound, 'counter.notFound', ['identifier' => $ctx->input()->identifier])   // 4xx ends the run; the door forms the typed failure
        : NodeResult::ok($this->handle(CounterRef::class, counterIdentifier: $ctx->input()->identifier));           // object value the node gives (readonly)
}
```

The `$this->result()` helpers below belong to the generated handlers and the door, which build the response through them; a node body never calls them.

| Status | Use |
|---|---|
| `Success` (200) | Read with data; also **every successful write over the wire** — a Process answers 200 with the reference value (or `@outcome` plus the fields the `gives` of its end node declares, `generated-code-recipes` Recipe 6; the reference value is the public key outside, `id` only without a key — inside the BC the command answer also carries the root `id`), never 201 (`ResponseStatus::Created` appears only inside the generated aggregate Create handler, which is family-internal and never a route) |
| `NoContent` (204) | Write succeeded, empty body |
| `ValidationError` (400) | DTO / invariant validation failed — thrown as a dedicated `ValidationException` in generated Validate classes (typed property `fields`: `list<array{field, reason, message, messageKey}>`; `field` = outer name per FieldMap as dot path with the list index at every door (`orderItem[0].qty`), `reason` = `missing` only for a validator marked `MissingValueValidatorInterface` (absent enum/date/number/boolean/value-list/child), else `invalid` — an empty string or `null` in a NOT-NULL string column is `invalid`; a body key the contract does not name answers `unknown` from the door, before the handler), caught **before** the catch-all `\Throwable`; precedes Rule evaluation (form before business). Payload `{"@type":"validation","fields":[…]}` |
| `RuleViolation` (422, Rules-Layer; requires `jardiscore/kernel` ≥ 1.1.0) | A bound Rule chain rejected the Command — built directly by the generated Guard-calling handler code, **never thrown**; at a Process door the 422 may also come from a dev body of the own BC (open `messageKey`, see the contract note above); `messageKey` is the catalog key when declared, not the body's `reject()` argument; payload `{"@type":"ruleViolation","rule","messageKey","context"}` (stable across Rule versions, `messageKey` = the catalog key when the entry declares one, i18n resolved by the surrounding app; an empty `context` is an empty object). A **technical** failure inside a Rule's existing-data check (DB down, timeout) is never a 422 — it falls through to 500. |
| `Unauthorized` / `Forbidden` (401/403) | Raised by middleware, not here |
| `NotFound` (404) | Target absent — payload `{"@type":"notFound","context"}` (`context` = the identifier(s) that failed to load, an object) |
| `Conflict` (409) | A write lost its read basis (stale write/delete) — payload `{"@type":"concurrencyConflict","reason","aggregate","context"}`; the handler catches the conflict exception before the catch-all `\Throwable`; a transient database conflict (typed `TransientConflictException`, contracts ≥ v2.6.0 / repository ≥ v1.6.0) is a 409 `stale_write`/`stale_delete` too, not a 500 — on MariaDB/MySQL inside a process it surfaces at the process bracket, not at the node (`generated-code-recipes` Recipe 11 Case B); repeat = client retry in a new transaction |
| `InternalError` (500) | Unexpected `Throwable`; the message is in `errors` |

**409 `violated` and `expected`.** A `duplicate` 409 carries `violated: list<string>` (outer field names of the hit unique columns, child fields as `<kindProperty>.<field>`; `[]` for unknown columns and for every `stale_write` / `stale_delete`) — see `generated-code-recipes` Recipe 12. The aggregate **write facade** `{Agg}` (family-internal, reached via the kernel seam / `$this->context(...)`) takes an optional `array $expected = []` after `string $version` on the root writers (`update{Root}`, `set{Root}Computed`): outer field name ⇒ the value the calling node read; the handler uses it as the CAS expectation instead of the freshly loaded state (`generated-code-recipes` Recipe 11, Case B). It is **not** part of the BC facade, the Rules door, routes, OpenAPI or any Command DTO; child writers and `Remove` do not carry it; an unknown key answers 500.

When you build a 400/404/409/422 by hand, use exactly these typed payloads — the same four forms every route, aggregate command and Process answers with. A dev body refuses with `NodeResult::reject(status, messageKey, context, errors)`; the package builds the form from the context keys it knows (400 `fields`, 409 `reason`/`aggregate`/`violated`, 422 `rule`; the rest is the form's `context`), a Process 4xx without a form (401/403/405) is passed through unchanged. The `messageKey` a node declares with `rejects(status, key)` (else the one named in `reject(...)`) is set on `data` after forming, for every 4xx status (also when it is not a field of the form, and also for a 4xx that has no form).

**Status staircase (Rules-Layer):** `400` (field validation) → Load → `404` (root not found) → `422` (business, Rule chain) → `404` (child / apply miss, after the Guard) → `409` (persist conflict) → `500` (technical) — a Command dispatch checks field validation first (cheap, local), then the Rule chain (potentially DB-bound), so a malformed request never pays for a existing-data check it can't pass anyway. A Process node calling a Command translates this deterministically through `MapResponse`: 2xx → `ok(data)`; a 4xx (including `422`) → a `reject` with the same status — the run ends, the engine routes no reject; `5xx → the exception path` (500, cause logged) — never a blanket `isSuccess() ? ok : route(OnFalse)` mapping, which cannot tell the two apart. Only a Dev decision inside a node may map a 4xx to a route.

**Process gate (before the first node).** A Process rejects a faulty command input before any node runs and before its transaction opens: the orchestrator `{Process}Handler::__invoke` starts with `ValidateInput` over the registry of `{Process}Validator` (emitted only when the input carries a rule), which checks the scalar fields and object items of the input by the rules of their types and value lists, and each command input field (a field with `accepts:`: single value, list, union) with the validator of every accepted command, the one the aggregate's own handler runs (a Remove has no validator and is not checked); other flat input fields carry no command validator. A field error answers 400 `validation` with `fields[]` in the gate's path form (`<property>.<field>`, `<property>[<i>].<field>`) at every door (route, `process()` facade, sub-process), so not even a 422 Rule node or a writing predecessor node comes first. The 400 lists one finding per field with `messageKey` `validation.missing` / `validation.invalid` (the package adds it from the finding's `reason`; a text the validator delivered stays untouched).

**TOCTOU boundary (v1, known limitation).** A Rule's existing-data check and the Command's subsequent Apply/persist are two separate steps — nothing in the generated Guard or CommandHandler locks between them. A concurrent write between the Rule's read and the Command's write can pass a Rule that would have rejected the now-changed state (time-of-check-to-time-of-use). This is a deliberate v1 boundary, not a bug: close it in the model — as a hard invariant in the DB schema (`UNIQUE`, `CHECK`, FK) that fails the write outright rather than relying on the Rule alone (`generated-code-recipes` Recipe 12), or as state with a conditional write (Recipe 11). A recheck of your own is not a Jardis artefact and has no place in a Rule body. A general recheck/optimistic-locking mechanism is not yet part of the generated code — that is a gap to build in Jardis or to report (§10), not to emulate.

`$this->result()` helpers:

- `setData(array)` — replace the flat payload (last writer wins; carry `@type`)
- `addData(string $key, mixed $value)` — additive field of the flat payload
- `addError(string $message)` — accumulates under the context name → on the wire `errors` is an object `{<context>: [message, …]}` (`{}` when empty, never `[]`) — use it for technical messages (a 500); the cause of a typed 4xx belongs in the form's `data` fields (`fields[]` / `context` / `rule`+`messageKey`), not in `errors`
- `addEvent(object $event, EventScope $scope = EventScope::Internal)` — accumulates only; the handler does **not** dispatch. Generated aggregate life-cycle events are `EventScope::Internal`. Publication is the **caller's** job after commit: a custom Process node that holds the command's response hands its events to a transport, or an Event ◇ node announces a Domain event with `NodeResult::route(Route::OnTrue)->withEvents(...)` — the events travel with the result, the handler collects those of a successful run as `EventScope::Domain` on the process response (see `generated-code-recipes` §1). `getEvents(?EventScope $scope = null)` filters by scope; with no argument it returns all scopes. `EventScope` is a `jardissupport/contracts` enum.

`DomainResponse`/`ContextResponse` (the Response pair), `TransformResponse` (the envelope mapper) and `BuildResponseData` (how a Process answer becomes the envelope's `data`) are **package classes of `jardissupport/response`** (`JardisSupport\Response\Data\Response\`, `JardisSupport\Response\Handler\Response\`; skill `support-response`) — the generated `{Domain}Context` only reaches them through `result()` / `transformer()`. The clock of a run is PSR-20: `{Domain}Context::clock()` resolves `SystemClock` through the kernel seam, and it stamps the envelope and the columns marked `auto: created|modified` in `Schema.json` (read ONCE per write); a test or a deployment substitutes it through the container key `CLOSURE_STAND_INS` (`{Domain}Context::CLOSURE_STAND_INS`, a map `className => stand-in`, e.g. a `FixedClock` under `SystemClock`). The `DomainResponseInterface`/`ContextResponseInterface` contracts, the `ResponseStatus` enum, and `EventScope` live in `jardissupport/contracts` (no dedicated dev-skill).
