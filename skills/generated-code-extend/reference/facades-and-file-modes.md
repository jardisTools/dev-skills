**AI path: a Rule guards a Command with a list existing-data check**. Prose in the Rule-stub docblock → the AI designs a Query that stays `closed` (the default stance) with `limit` → MCP `save_queries` → `save_closures` with `reads:` pointing at that query → `build` → the Rule body reads over the kernel seam with `limit: 1` and decides over `total`. Example: "Customer has open invoices" — Query `openInvoicesByCustomer` (`closed`, `limit: 1`) → `total > 0` → `RuleResult::reject(...)`. **Reader hint:** if a Rule or Process node body names a `Get…Handler::class` the build does not generate (e.g. a stale `Get{Agg}SelectorHandler` reference), the drift category `dev_code_dangling_handler` (`internal/devcodescan`, `appsvc/rules_drift.go`) flags it as "Dev-Code anpassen" (adapt dev code) — comment-blind, it does not read the docblock recipe.

**Three file modes from the generator:**

- **ForceOverwrite** — rewritten on every build. The **entire** `{Agg}/` tree, Domain/BC facades, the hermetic `{BC}Process` facade, Process DTO (`Command/<Name>.php`) + orchestrator (`Command/Handler/<Name>Handler.php`) files, event-data classes (`Event/<EventClass>.php`), and the Rule-Layer hermetic Guard `{BC}/Closure/Guard/Guard<Command>.php` (the verdict class `RuleResult` is the package's `JardisSupport\Response\Data\RuleResult`, not generated). A domain with ≥1 catalog Closure additionally gets exactly ONE hermetic file outside `src/`, `tests/Unit/Closure/{Domain}/ClosureTestCase.php` (the stand-in helpers, regenerated on every build); the per-Closure test next to it is yours, never generated. Every build of a domain with a BC that has an aggregate also generates the test scaffold `tests/Support/{Domain}/` (namespace `Tests\Support\{Domain}`): `{Domain}TestCase.php`, `Test{Domain}.php` and one `{BC}WriteHarness.php` per built BC with an aggregate — never hand-edited; Fakes you add in the same folder stay untouched. How to use it → `foundation-testing` §6.
- **CreateIfNotExists** — written once, then preserved. `Config/.env*` files; Process custom-node stubs `{BC}/Process/{Name}/Command/Handler/Action/<NodeClass>.php` (one file per node).
- **`@node-id` body-preserve** — Process custom nodes **and sub-process nodes**. On rebuild the developer body is preserved, keyed by the `@node-id` marker. Methods the developer changed and the developer's own methods always stay. An untouched generated helper method (anything but `__invoke`, which always stays) stays only while a kept method uses it — a call (`$this->`, `self::`, `static::`, also nullsafe) or its name inside a string literal (case-insensitive); a previously appended, unused helper disappears at the next build. For sub-process nodes: the first build emits a typed Dev-Stub (real Sub-input field names, the inner-door call, the `MapResponse` mapping with the inner events, open places for underivable values); subsequent builds preserve the developer body unchanged. (The Process-Designer "Force" build path can deliberately overwrite a node body instead.) **Rule stubs** (`{BC}/Closure/<RuleName>.php`) use a related but distinct, per-method merge rule (no `@node-id` — a Rule has no single declaring node): an **untouched** generated method migrates wholesale to the new signature/body, a **hand-edited** method is kept 100% verbatim (including its docblock) — for every generated method on a DeveloperOwned class, not just `__invoke`.

**Aggregate facade mechanics.** The aggregate's public surface for reads (absent for an aggregate with no read door at `domain` or wider — no `{Agg}Read`, no route; commands and queries stay usable through the kernel seam and from processes) is `{Agg}/{Agg}Read.php` (`extends <Domain>Context`), reached via `$bc->{agg}()` → `handle(<Agg>Read::class)` — the BC facade's public surface (G2), public FQN `<Domain>\<BC>\Model\<Agg>\<Agg>Read`. The write facade `{Agg}/{Agg}.php` (public FQN `<Domain>\<BC>\Model\<Agg>\<Agg>`) hosts the commands + `event()` and is reached only family-internally via the kernel seam, `$this->handle(<Agg>::class)` — never through `$bc->{agg}()`. Both facades are fully regenerated (ForceOverwrite) — there is no body-merge, no `@flow-id`. You never add methods to either; new aggregate behaviour is modelled in the Designer (structure) or authored as a Process (behaviour). ClassVersion resolves a versioned variant `<Domain>\<BC>\Model\<Agg>\v{N}\<Agg>` (write) or `…\v{N}\<Agg>Read` (read) when the per-call `$version` argument is non-empty (see `generated-code-versioning`).

**Read base — the read ways of an aggregate (hermetic, emitted on every build; the stance of each way is its row in `Doors.json`, default `outside`, and only a way at `domain` or wider is a method of `{Agg}Read`).** Without a public unique key the ways are `ById`/`ByIds`, with one `By<Key>`/`By<PluralKey>` only — `ById`/`ByIds` then stay internal (kernel seam) and have no row:

| Method | Query DTO | Response data block |
|---|---|---|
| `get<Agg>ById($q)` | `Query\<Agg>ById { id }` — type follows the PK | `['@type' => '<agg>'] + <root fields flat>`, children `{Child}Response` objects; nothing found → `[]` |
| `get<Agg>ByIds($q)` | `Query\<Agg>ByIds { ids }` — `list<PK type>` | `['@type' => '<agg>List', 'items' => list<{Agg}Response>]` — objects, **no `[0]` collapse** |
| `get<Agg>By<UniqueKey>($q)` | `Query\<Agg>By<Key> { <keyField> }` — camelCase column, no entity prefix | `['@type' => '<agg>'] + <root fields flat>`, children `{Child}Response` objects; nothing found → `[]` |
| `get<Agg>By<PluralKey>($q)` | `Query\<Agg>By<PluralKey> { <keyField>s }` — `list<key type>` | `['@type' => '<agg>List', 'items' => list<{Agg}Response>]` — objects, **no `[0]` collapse** — only on an aggregate WITH a unique key |

**Reading the data block in PHP.** Only the root level is spread into the array: `getData()['counterNumber']` is correct for a root field, but every child is a typed `{Child}Response` object (a list of them for `many`) — `getData()['registerRelation'][0]->register->obis`, never `…[0]['register']` (an array access on an object throws at runtime; PHPStan does not see it, `getData()` is `array<string, mixed>`). The `items` of a bulk read are `{Agg}Response` objects as well (`$item->counterNumber`). The flat `<agg>List` is the exception: it is no `DomainResponse` but a `ReadResult` (`JardisSupport\Response\Data\ReadResult`) — `->items()` are plain arrays (`$list->items()[0]['id']`), `->total()`, `->first()`, `->isEmpty()`. Shape reference: `generated-code-recipes` Recipe 6.

`By<UniqueKey>` exists exactly once per aggregate — the identifier chain picks the unique business key (e.g. `getCounterByIdentifier(new CounterByIdentifier(identifier: $i))`); an aggregate without a unique key gets only ById/ByIds on its read facade. An aggregate WITH a unique key gets `By<UniqueKey>` and the bulk variant `By<PluralKey>` (e.g. `getOrderByOrderNumbers`) INSTEAD of ById/ByIds (see Bulk-read recipe below). Further `get<Agg>By<Custom>` methods come from queries DECLARED in the BC's `Queries.json` (`Source.json` has no `queries:` text path — a leftover one is rejected, `V-QDEF-23`); `<agg>List(<Agg>ListFilter)` is the flat list — **not** part of the uniform read base above: it is an ordinary DECLARED query in the BC's `Queries.json` (the base list, seeded there once when an aggregate is first saved), so an aggregate whose `Queries.json` carries no such query has no `<agg>List` method. A suffix-less `get<Agg>` does not exist. The ids are the **internal**, family-wide handle of the domain API (the ById/ByIds query classes and handlers keep being emitted regardless of a unique key and are reached over the kernel seam; only without a unique key are they also read doors) — the facade is no public REST surface; exposure is the surrounding app's decision — and FK/child internals stay encapsulated either way.

**Tenant and user markers (`tenant` / `user` on the aggregate entity).** For an entity with a `tenant` or `user` marker, the Query and Command DTOs that address or write it do not carry the marked column as client input; the tenant is the first constructor argument of the generated `{Query}Filter` (no default), so a read over the kernel seam without the scope is a type error. The generated `routes.php` fills `tenant`/`user` from the request attributes (`RequestAttribute::TENANT` / `::SUBJECT_ID`, `jardissupport/contracts` >= 2.17) and puts the per-route middleware `RequireRight` (right of the endpoint, `jardiscore/app` >= 3.2) and `RequireRequestAttribute` in front: a missing right or attribute answers 403 before the handler, never 500. Hand code reads tenant and user from the process DTO (`$ctx->input()->tenant` / `->user`, filled by the door) and passes them on explicitly, never from client input. A `tenant` marker filters every read variant of the root, and a child entity whose column `adopt`s the effective tenant column of an ancestor is filtered by derivation (every query rooted at it gets the tenant filter, the value comes from `adopt`); a `user` column is only a write value. The write answer and a 404 context carry only the key, not the scope. A `writeOnly` column is absent from every Read DTO, public list item, event payload and command answer. A hand-written family-internal check (verify a stored digest) reads it through a declared query that stays `closed` or `domain` (no `Doors.json` row at `outside`), called over the kernel seam (`$this->context({Handler}::class, $filter)()`); the generated internal query handler projects the column, no outer form ever does.

> **DTO class names vs. alias.** The read/write DTOs are really named **`<Agg>`** (Command, e.g. `Counter`) and **`<Agg>ById` / `<Agg>ByIds` / `<Agg>By<Key>`** (Query, e.g. `CounterById`) in their own `Command\` / `Query\` namespaces. A `Command…` / `Query…` prefix (e.g. `CommandCounter`, `QueryCounterById`) is only a **`use … as …` alias defined inside the aggregate's write facade** (Command) **or read facade** (Query) signatures, not the real class name; examples in this skill name the real class. Code **outside** either facade must import the real name (`use …\Query\CounterById;`) or add its own `as` alias.

**Bulk-read recipe** (the recipe forks on whether the aggregate has a public unique key):

An aggregate **WITHOUT** a unique key: list items lead with the root id, so the set pattern is:

```php
$list    = $bc->heartbeatSignal()->heartbeatSignalList($filter);
$ids     = array_values(array_unique(array_column($list->items(), 'id')));
$records = $bc->heartbeatSignal()->getHeartbeatSignalByIds(new HeartbeatSignalByIds(ids: $ids))->getData()['items'];   // list<HeartbeatSignalResponse> objects
// match per id (`$record->id`) — every aggregate record carries it
```

An aggregate **WITH** a unique key: the list SELECT leads with that key column instead of `id`, and the bulk read goes through the `By<PluralKey>` variant:

```php
$list    = $bc->order()->orderList($filter);
$keys    = array_values(array_unique(array_column($list->items(), 'orderNumber')));
$records = $bc->order()->getOrderByOrderNumbers(new OrderByOrderNumbers(orderNumbers: $keys))->getData()['items'];   // list<OrderResponse> objects
// match per orderNumber (`$record->orderNumber`) — every aggregate record carries it
```

Edge behaviour (existing infrastructure semantics, nothing new underneath): empty input → empty list · duplicates → deduped (IN semantics) · missing keys/ids → partial result, no error (consistent with ById/By<Key> → `null`) · no order guarantee. Family-internal callers (kernel seam) can still use the ById/ByIds handlers either way — the read facade, the list-item handle and the public surface (OpenAPI) are key-only when a unique key exists.

**Process facade mechanics.** `{BC}/Process/{BC}Process.php` (`extends <Domain>Context`) is hermetic — fully regenerated on every build (`ForceOverwrite`, no body merge, no `@process-id`). It carries one thin-dispatch method per process, which cuts the answer per outcome (`ProjectOutcome` with one `OutcomeForm` per `gives.name`; an answer without `@outcome`, or one the facade has no form for, is a 500); the process logic lives in the orchestrator's custom-node bodies under `{BC}/Process/{Name}/Command/Handler/Action/`. **Process stance:** a process whose row in the block `process` of `Doors.json` is `closed` is a pure sub-process of its own BC — the facade emits **no method** for it (it is only reachable as a sub-process node inside another process of the same BC). `domain` gives the facade method (also for the other BCs of the domain), `outside` adds route and right, `open` a route without login and right (default `outside`). The stance controls only the doors; the process DTO, orchestrator, and node stubs are always generated. A sub-process node or Cross-BC-Call onto a FOREIGN door needs the stance `domain` or wider there (`V-CONSUMED-EXISTS`, blocker). The stance is set in the door table of the BC page or with `save_doors`; the keys `subprocessOnly` and `visibility` are retired (`V-DOOR-0`).

**BC facade caches nothing** (each `->{agg}()` / `->process()` / `->{command}()` is a fresh `handle()` resolve). **All facades** delegate through `context()` / `handle()`. **Never** instantiate handlers directly (V2/V3).
