### 2. Where customization goes — the aggregate has no edit slot

The aggregate tree is hermetic; **nothing** under `{Agg}/` is a developer override point. There are exactly four sanctioned ways to change behaviour:

| You want to… | Do this |
|---|---|
| Add or change **behaviour** (validation, calculation, cross-aggregate coordination, event transport, external calls) | Model a **Process** in the Process Designer. Generator emits the DTO + orchestrator + node skeleton under `{BC}/Process/{Name}/Command/` and `Command/Handler/Action/` (plus `Event/` for event nodes), and a thin-dispatch method on the hermetic `{BC}Process` facade (`$bc->process()`). Your logic lives in the custom-node bodies (`@node-id` preserve); further hand code exists only at the places of §10. A process has **no aggregate ownership** and may coordinate several aggregates. |
| Change the aggregate's **structure / invariants** (entities, relations, keys, `required`/`depend` rules, commands/queries) | Re-model the aggregate in the Aggregate Designer (`Aggregate.json`) and rebuild. The generated tree changes accordingly. |
| Provide a **versioned variant** of a stub class (node, Closure/Rule, Domain Service; tenant / feature-flag) | Put the variant in a `v{N}/` subdir next to the stub (`Action/v{N}/<Node>.php`, `Closure/v{N}/<Name>.php`, `Service/v{N}/<Name>.php`) and select it **per call** via the `$version` argument threaded through every facade method — there is no domain-wide default (the Domain facade is `final`, `{Domain}Context` hermetic). ClassVersion (`LoadClassFromSubDirectory`) resolves `…\v{N}\<Class>` before the baseline. A hermetic class (anything under `Model/{Agg}/`, a handler, a facade) takes no variant: add behaviour in a Process or re-model instead. **Note:** a versioned build (`version: "v2"` on `build`/`build_process`/`build_domain`, CLI `--version`) writes the fresh `final` stub frame of each stub class into its `v{N}/` subdir (same signature, namespace `…\v{N}`, no `extends`; the body you write survives rebuilds) — never a hermetic class. See `generated-code-versioning`. |
| Guard a Command with a **business rule / existing-data check** before it runs (Rules-Layer) | Declare a catalog entry + endpoint binding in `Closures.json` (BC-level, sibling of Process/Steckbrief). Generator emits a Rule stub under `{BC}/Closure/{RuleName}.php` (guard-bindable shape: `__invoke({Cmd}DTO): RuleResult` — one of several signatures the general Closure contract allows, §1 "Vocabulary glossary") plus a hermetic Guard closure that runs the bound chain (AND, short-circuit) ahead of the Command. Your logic lives in the Rule stub body — existing-data checks stay within your **own BC** (M9), via the read facade or directly via the kernel seam (`context()`) for a BC-internal read; anything needing a cross-BC read or a multi-step/side-effecting flow is process territory, not a Rule. **Until you implement it, the stub throws** (500), it does not fail open — see the Rule stub row in §1 and `generated-code-recipes` §3 Troubleshooting. |

**Migration note (path collision).** In the pre-Platform-removal layout a file directly under `{Agg}/Command/…` was a **shadow override** that the ClassVersion reader (`segmentNames: ['', 'Platform']`) found *before* the generator class under `{Agg}/Platform/Command/…`. The Generator writes to `{Agg}/Command/…` itself (ForceOverwrite) — an old baseline override at that path **collides** and is overwritten. There is no auto-migration. To migrate such an override: move the behaviour into a Process (`{BC}/Process/`), or re-model in the Designer. The build deletes the orphan `{Agg}/Platform/` directory on regen.

**Domain support code.** There is no place for value-object or helper classes: a value is checked by the model (column type, value list, process input type, Validator) or by a Closure/Rule; a Domain Service lives at `{BC}/Service/{Name}.php`, the one location of §10 — the rule fixes the place, nobody chooses it by convention. The Generator owns `Command/`, `Command/Handler/`, `Command/Handler/Action/`, and `Event/` of a process; hand code in it stands only in the node bodies of `Action/`. A directory directly under `{BC}/Process/` that is not a process of the model and holds no generated node file (no `@node-id` marker) is **not deleted** — the build warns about it with its path in the build result; it is a stray, no hand-code place. An orphaned, generator-created process directory (the process was removed from the model) is deleted **with its whole content**, developer code included.

**Generated Service stubs sit at one place.** The Service stub of a Cross-BC-Call or External-Call node is `{BC}/Service/<Name>.php` of the calling BC — you choose only the business service name (or leave it to the target-derived default), never a directory or a tier. A developer body an earlier build left at an old place moves to `{BC}/Service/` with the next build. See §1 for the write mode (header-aware merge).

**FieldMap + Entity Validators are generated** (`{BC}/FieldMap.php`, `{BC}/Entity/Validation/<Entity>Validator.php`, ForceOverwrite) — both are **BC-level** (BC-rooted, one per BC table over all BC tables), not aggregate-scoped. The FieldMap exposes one `{table}Columns()` write-map method per BC table. Logic that must participate in those generated entry points belongs in a **Process node** that runs before/after the aggregate call — never as an in-place edit of the FieldMap or validator. A node does not repeat what the generated validator and the FieldMap already do (field type, value list, length, mapping): only what the model cannot express is node logic.

**Validators for "absent" (rule).** A developer-written validator that reports an absent value must implement `JardisSupport\Contract\Validation\MissingValueValidatorInterface` (jardissupport/contracts ≥ 2.3.0); the generated `ValidationException` takes `fields[].reason` from the validator kind (validation ≥ 1.2.0), so only this marker yields `missing` — wording of the message is irrelevant, a finding without a kind is `invalid`.

**Bulk-read warning.** Every generated collection query handler (`get{Agg}ByIds`, `get{Agg}By{Key}s`) logs one warning through the Kernel logger when called with more than 100 keys (`BULK_WARN_ABOVE`); it never aborts — chunk large key lists in the caller.

**Rename & rebuild (object rename).** Domain, BC, aggregate, and process can be renamed in the Designer **even after a build exists**. A rename updates the definition and all referencing JSON documents immediately (`subProcess`, `consumedCalls` — cross-BC included, `accepts`), stamps the renamed artefact and every affected consumer "rebuild needed", and leaves a rename trace; the **next build** pulls the code along. What that means for your code:

- **Developer code survives every rename.** Dev-code-bearing process trees are **moved** (not deleted + regenerated): file **bodies** stay byte-identical; only the mechanical header (`namespace` line + `use` lines pointing at renamed generated namespaces) is patched — PSR-4 stays intact, PHPStan stays green. Hermetic trees (aggregate) are simply regenerated under the new name and the old tree is cleaned up. `v{N}/` directories move physically with the tree (no version-specific namespace follow-up yet).
- **Consumers show a reason note.** A consumer process whose `consumedCalls`/`subProcess` reference was rewritten carries a persisted note (old → new, affected calls), visible in its detail panel; a successful build of that consumer clears note + stamp.
- **Hand code outside the output tree is NOT rewritten.** App/bootstrap wiring or external event listeners that mention renamed FQCNs by hand get a naming warning in the rename preview — updating them is your job.
- **Node rename** (Ticket panel) keeps the `@node-id` body across the file rename; event-mode nodes get their `Event/` class swept along.
- **Node class names are PascalCase, derived from the model name.** The generator derives ONE class name per node: `ucfirst(name)` (an Event ◇ node `mode: async`: node class `ucfirst(name)` + `Node`, event-data class `ucfirst(name)`). File, class and FQCN of node **and** event all come from that one derivation — a model name `checkStock` yields `CheckStock.php` / `final class CheckStock` (PSR-12). Write node names in PascalCase; a lowercase name still builds but the validator warns `V-PROC-NAME-CASE` and names the derived class. A project built before this rule (`checkStock.php`, `Event/stockChecked.php`) migrates on its **next build**: the node file is renamed by its `@node-id` marker with the developer body byte-identical and the old file removed, the event data class is rewritten under the new name — and **every rename is reported as a build Hinweis** (`Knoten <id>: checkStock.php → CheckStock.php, Body übernommen`; for an Event `… FQCN geändert: Listener-Importe prüfen`). The event FQCN changes with it: **hand-written listeners/imports of `…\Event\stockChecked` are yours to update** (they sit outside the output tree and are not rewritten).
- Renaming back (new → old) is a normal rename with the same rules; a rename preview (impact list incl. foreign-BC consumers and dev-surface hints) runs before every level rename in the UI.

**A Closure/Rule catalog-entry rename does NOT follow the rule above — your stub is not moved.** Renaming a `Closures.json` entry (Closure-Editor or MCP `rename_closure`) rewrites the JSON catalog key, every binding chain naming it, every other Closure's `uses` (Set member or free reference alike), and every process Rule-node's `rule` field — but the **developer-owned stub file itself stays where it is**, under its old class name; the rename response carries an explicit warning ("generated dev stub … was not moved — rename it by hand, or let the next build regenerate a fresh one under the new name"). Move your `__invoke()` body yourself, or accept a freshly generated (unimplemented, throwing) stub at the new path. Deleting a Closure still bound to ≥1 chain, referenced by ≥1 `uses`, or used by ≥1 process Rule-node is blocked with `409 IN_USE` and the list of referencing bindings/processes/sets; `force=true` deletes anyway and leaves those references dangling.

### 4. Decision tree — "I need to…"

Every row resolves to a **modelled artefact** (Process, Query, Closure), a **Designer re-model**, or a **versioned stub variant** — never an in-place edit of the aggregate.

| Need | Action | Pattern |
|---|---|---|
| Validate a domain concept (OBIS, IBAN) | Express it in the model: a column type or value list in the Schema, the process input type, or a Closure/Rule with the check in its body, used from a node. No free value-object class exists (§10); a check the model cannot express is a missing Jardis capability — report or build it, do not substitute | Specification (Closure) |
| Load data from an external API | Model an **External-Call** node in the Process Designer — the generator emits a Service stub at `{BC}/Service/`, pre-wired with a PSR-18 `resource()->httpClient()` scaffold + a transport-error docblock (§1). If no node kind fits, a Jardis capability is missing: build it in the package or generator (when working on Jardis itself) or report it as an issue (when working on an app) — never a hand-built substitute. | Adapter |
| Read from another BC | Model a node whose `consumedCalls` point at the foreign BC's `{Agg}Read` — that is a **Cross-BC-Call** node by itself — declare `crossBcCall: {ServiceName}` on it so that one shared Service serves every node with the same target (without it the generator derives one shared Service per target, named from the target's facade segments after the domain prefix and its call key); the generator emits the target-facade wiring (reusing the node's `consumedCalls[0]`) plus a Service stub with pre-wired `handle()` calls and an ACL docblock nudge (§1); never import another BC directly. Target: the foreign `{Agg}Read` methods. | Adapter |
| Read a BC-specific setting from the environment | Declare the key in `BC.json` `env[]` (MCP `save_bc_env`), write the value through `save_runtime_env` block `domain` into the one project `.env`, read it in the body with `$this->resource()->env('<KEY>')`; an undeclared key is refused (`V-RT-7`) | — |
| Store a value the process derives (sum, counter) | Mark the column `computed` in the Aggregate Designer (field table switch / MCP `save_aggregate` node field `computed`): it leaves every Create/Set/Add/Update command and the OpenAPI request (a body naming it is `400 unknown`; Read, list and Akte keep it). Write it from a node body through the family-internal `$this->handle({Agg}::class)->set{Entity}Computed($dto)` — own event `{Agg}[{Fragment}]ComputedUpdated`, no route, no BC-facade method | Facade / Command (`generated-code-recipes` Recipe 13) |
| Write to another BC | Model a **Cross-BC-Call** node targeting a door of the foreign BC at stance `domain` or wider — its **process** or a **command door** (never its aggregate write facade; `V-CONSUMED-EXISTS` checks the owner's stance); the generated Service DTO-translates your input, calls `$this->handle({TargetBC}::class)->process()->{process}($dto)` (or the command door `{lcfirst(command)}($dto)`), and maps the response back into your own vocabulary (ACL) — never a direct aggregate write on the foreign BC. See `generated-code-recipes` §2 Recipe 9. | Adapter |
| New BC-level operation / coordinate several aggregates | Model a **Process**. Generator emits DTO + orchestrator + node skeleton under `{BC}/Process/{Name}/Command/` and `Command/Handler/Action/`, and a thin-dispatch method on the `{BC}Process` facade (`$bc->process()`). Logic lives in the custom-node bodies. | Facade + Workflow |
| New aggregate command/query, or tighten an aggregate's invariants | Re-model the aggregate in the Aggregate Designer (`Aggregate.json`) and rebuild — the generated command/query/validator tree changes with it. A new **query** surfaces inline on the read facade `{Agg}Read.php` (`$bc->{agg}()`, the BC facade's public surface); a new **command** surfaces inline on the write facade `{Agg}.php`, reachable family-internally (`$this->handle({Agg}::class)`) and from outside only through the stance of its row in `Doors.json` (`domain`/`outside` = facade door `{BC}::{command}()`) — or model a Process around it to expose it via `$bc->process()`. There is no slot to hand-edit either facade. | Designer |
| Something that applies to every door equally and needs no domain model (session check, CORS, request id, rate limit) | **Not a process node, not a closure**: PSR-15 middleware at the HTTP front door, registered with `Routes::middleware()` — see `core-app`. A rule that needs the domain model ("may this user see this project") stays a Rule/Process. A missing general middleware is a gap to report in `jardisCore/app`, not project code. | Chain of Responsibility |
| Add a calculated field to a query response | Declare the column `computed` in the Aggregate Designer and write it with `Set{Entity}Computed` (Recipe 13): Read, list and Akte then carry it. A value the model cannot express is a missing Jardis capability — report or build it; no enrichment in a node body | Designer |
| Emit / route a domain event to a transport (Kafka, webhook, …) | Announce it with an Event ◇ node; the transport is delivery code in `App/**` that publishes the answer's Domain events after the commit and carries no business logic — see `generated-code-recipes` event-transport recipe. The generated `<Agg>EventRouter` is hermetic. | Adapter (delivery layer) |
| Remove an entity with a NOT-NULL `depend:` parent | **Not allowed** — the Build rejects Remove on an entity another entity depends on via NOT-NULL FK (F3.6 / V8-sibling). Re-model the aggregate to drop the NOT-NULL constraint, or model a soft-delete Process so dependents stay resolvable. | Designer + Process |
| Remove a `required` child (no `Remove…` command exists, or the last entry refuses to delete) | **By design** — a relation marked `required` (default; opt-out `required: false`) is an existence invariant. **`required·one`** emits **no `Remove…`** (only `Set…`); **`required·many`** keeps `Add…`/`Remove…(id)` but the Remove handler carries a **min-guard** that throws when count would hit 0 (Create also demands ≥1, `Count::min(1)`). To allow emptying, re-model as `required: false` and rebuild. | Designer (Aggregate.json) |
| Tenant- / feature-flag variant of a stub class (node, Closure/Rule, Domain Service) | Put the variant in the stub's `v{N}/` subdir and select it **per call** via the `$version` argument — no domain-wide default (see `generated-code-versioning`). Resolution is wired; a versioned build writes the fresh stub frame, you write its body. | ClassVersion |

### 5. New-code locations — the places of the one table (§10)

```
<Domain>/<BC>/                               ← Bounded-Context dir
├── Closure/                                  ← ★ Closure catalog (sibling of Process/ and Model/)
│   ├── <RuleName>.php                       ← ★ your body (DeveloperOwned, tag RuleClass) — 0..n typed
│   │                                            params per `input[]`, RuleResult or scalar per `output`
│   ├── Guard/Guard<Command>.php             ← hermetic AND-chain closure (Generated, ForceOverwrite)
│   └── v{N}/<RuleName>.php                  ← versioned Closure override (ClassVersion)
│                                               (the per-Closure test under tests/Unit/Closure/ is yours to write from examples[],
│                                                against the generated ClosureTestCase — §1)
├── Service/                                 ← ★ Domain Services (sibling of Closure/ and Process/), the one location
│   ├── <ServiceName>.php                    ← ★ your body (Domain Service stub); own BC read-only, foreign BC only through its doors
│   └── v{N}/<ServiceName>.php               ← versioned Service override (ClassVersion)
├── Process/                                 ← BC-level Processes (sibling of Model/); hand code only in the ★ Action/ bodies
│   ├── <BC>Process.php                      ← hermetic facade (Generated, ForceOverwrite) — $bc->process()
│   └── <Name>/
│       ├── Command/                         ← Generator-owned (ForceOverwrite, hermetic)
│       │   ├── <Name>.php                   ← Input DTO
│       │   └── Handler/
│       │       ├── <Name>Handler.php        ← orchestrator (regenerated, not edited)
│       │       └── Action/<NodeClass>.php   ← ★ custom-node body — your process logic
│       │                                      (CreateIfNotExists + @node-id preserve)
│       └── Event/<EventClass>.php           ← event-data classes (Generated, ForceOverwrite)
└── Model/<Agg>/                             ← ★ GENERATED, NEVER EDIT (whole tree, no Platform/ segment)
    └── … (read/write facades, Aggregate, Command, Query, Event, Repository)   ← FieldMap + Entity/ are BC-level (one level up), NOT in the aggregate tree
```

Outside `src/`, a build additionally writes the test-support scaffold `tests/Support/{Domain}/` (never hand-edited, see §1 "ForceOverwrite" and `foundation-testing` §6).

Hand code stands only at the places of §10: node bodies under `{BC}/Process/{Name}/Command/Handler/Action/`, Closure/Rule bodies, Domain Services under `{BC}/Service/`, and `App/**` delivery code. The Generator owns the rest of the process tree (`Command/` DTO + orchestrator, `Event/`). The aggregate tree `{BC}/Model/{Agg}/` is hermetic: never add or edit files there; it takes no `v{N}/` variants (§2).

There is no aggregate-root file to extend, no `{Agg}/Api/` registry, and no `Platform/` directory. The aggregate's two facades host the inline registries of generated Commands (write facade, family-internal via the kernel seam) and Queries/lists (read facade, reached via `$bc->{agg}()`, the BC facade's public surface); BC-level operations route through the `{BC}Process` facade via `$bc->process()`.

### 6. Implementation levels

No skipping, no parallel levels. PHPStan L8 + tests + review green between levels. All hand-code levels are expressed at the places of §10 — the aggregate itself is generated.

| # | Level | Where | Anchor |
|---|---|---|---|
| 1 | Aggregate structure + invariants | Aggregate Designer (`Aggregate.json`) → generated `{Agg}/` tree | `design-draft-schema` |
| 2 | BC-level processes (behaviour) | Process Designer: `{BC}/Process/{Name}/Command/` (DTO) + `Command/Handler/` (orchestrator) + `Command/Handler/Action/` (one `<NodeClass>.php` per node) — your logic in the custom-node bodies (`@node-id` preserve) | `jardissupport/workflow` |
| 2a | Endpoint business rule (existing-data check gate before a Command runs) | `Closures.json` catalog + binding → `{BC}/Closure/{Name}.php` stub, your logic in `__invoke()` (own BC only via the kernel seam, M9). **A stub not yet implemented throws (500), never `RuleResult::pass()`** — implement it before binding it live. | — (Rules-Layer, no separate package skill) |
| 3 | Business validation used by a process | modelled: column type / value list in the Schema, process input type, or a Closure/Rule — used from node bodies; no free value-object class | `jardissupport/validation` |
| 4 | Domain Services (external data, calculations; a foreign BC only through its doors) | `{BC}/Service/{Name}.php`, called from a node body via `handle()` | `generated-code-extend` §10 |
| 5 | Workflows / long-running flows | Process graph (`definition()` of `{Name}Handler`, run by the same door) + custom nodes | `jardissupport/workflow`, `generated-code-workflow-api` |
| 6 | Event transport | Event ◇ node announces the Domain event; `App/**` delivery code publishes it after the commit (the generated `<Agg>EventRouter` is hermetic) | `jardisadapter/messaging` |
| 7 | Non-functional (cache, logging) | Process node + DomainKernel wiring | `jardisadapter/cache`, `jardisadapter/logger` |
