#### 2.2 Aggregate (designer graph)

Door: MCP `save_aggregate` (`graph.nodes`, `graph.edges`, `graph.adopts`), `add_aggregate`, `suggest_aggregate_edges`, `set_aggregate_tables`, `rename/delete/duplicate_aggregate`, `discard_aggregate_draft`; UI aggregate designer (node panel, edges, API tab for rule chain). Exactly one root entity with `erm: one`.

| Setting | Allowed values | Effect |
|---|---|---|
| Child `erm` | `one` / `many` | `many`: `Add{Singular}`, `Update{Singular}` and `Remove{Singular}` child commands, a child list in the create command. `one`: `Set{Child}` always, `Remove{Child}` only when the child is optional |
| `source` | table name (alias allowed) | one aggregate entity per table; the table must exist in the schema (R1) |
| `relates` (edge `sourceCol`/`targetCol`, `extraConditions[]`) | join condition between parent and child | defines the FK link; `extraConditions` carry polymorphic discriminators |
| `required` | default `true`; `false` explicit; forbidden on root | `many` + required: create requires a non-empty list (400 via `CountMin`) and removing the last entry is refused; `one` + required: create requires the child (`NotBlank`) and no `Remove{Child}` is generated for a plain required child; `false`: optional child, `Remove` available |
| `adopt.onCreate` | `'"const"'`, `'"__UUID7__"'`, `'"__UUID4__"'`, `<entity>.id`, `<entity>.field` | column filled once at create, removed from the command DTO. `<entity>.id` = FK from an ancestor; UUID varchar needs length ≥ 36 |
| `adopt.sync` | `<entity>.field` | column re-filled on every persist (field inheritance) |
| `depend` | `<column>: <entity>.id` (target = child or sibling, not `many`; no cycle, no both directions) | persist cascade: the target is persisted first and delivers the generated id; FK removed from the DTO. Not combinable with `adopt` on the same column |
| `identifier` | `{stage: column\|uniqueColumn\|pk, column}` | declares the public identifier explicitly (otherwise guessed by a 3-stage cascade; ID-2 suggestion). The key is the public identifier alone; a tenant is never part of it (the `tenant` marker filters and addresses, path and write answer carry only the key, not the tenant). Child `many` needs a dedicated unique identifier column, else PK fallback (R7). Declare `identifier {stage: column, column: identifier}` on every child that has an identifier column; an undeclared pick raises finding ID-2 |
| `computed` | `[<column>…]` | columns the PROCESS derives (sums, counters): they leave every Create/Set/Add/Update command and the OpenAPI request, Read/list/Akte keep them; written through the family-internal `Set{Entity}Computed`. The column must be nullable or carry a DB default (V-CALC-1), never PK, public identifier, FK or adopt (V-CALC-4) |
| `tenant` / `user` (entity keys, root AND child) | `tenant: "<column>"` (one column) · `user: {"<column>": "onCreate"\|"onWrite"}` on varchar/char/uuid/integer data columns | `tenant`: the column holds the tenant of the signed-in user; `user`: the columns that receive the bare id of the signed-in user (`onWrite` = Create and Update, `onCreate` = Create only, the author stays the author). The value comes from the request context, never from the client: the column leaves every input contract (path, query, body, OpenAPI request; a client sending it in a body gets 400 `unknown`, except where the key is tolerated and dropped: inside the command object of an `accepts:` entry and, for an `onCreate` column, at the Update door) and is set at every write door. A `tenant` column also filters EVERY read variant of the root (Akte, `By{Key}s`, list, every query rooted on it) and is absent from every read output; a `user` column is a value at writing, never a read filter, and stays visible. A child entity that takes over the effective tenant column of an ancestor via `adopt` (transitively over the levels) is tenant-filtered by derivation: every query rooted at it carries the automatic tenant filter and the value comes from `adopt`, not from the session. Never PK, key, adopt, computed (`V-TENANT-2`; a marker on the `adopt` column of a derived child is refused too). The markers act only in a world with login (project `middleware` carries `session`): then every aggregate root carries a `tenant` marker (`V-TENANT-1`, Blocker; exempt: a BC with `loginIdentity: true`, brought by the Access blueprint). Missing right or attribute at runtime → 403 from the package middleware (`RequireRight` / `RequireRequestAttribute`, `jardiscore/app` >= 3.2) before the handler runs |
| `access` (aggregate root only; optional exception) | `"everyone"` · `{"owner": "<Aggregate>", "via": "<column>"}`; omit = keep, `""` = delete | **protection is the rule:** in a world that protects (login AND groups AND a bounded context without `loginIdentity`) the records of every root TABLE are visible per record without any statement (protection follows the root table, not the aggregate; several aggregates on one root table are allowed, carry the same statement and share sight and number; the table gets ONE number in the access-type list `Domain.json` `access.types`, read only in `jardis://domain/{domain}/manifest`, kept by one reconciliation on every door): `everyone` = released, the table carries no sight; inheriting = takes over the sight of an owner on a protected root table of the SAME bounded context through a root column. Different statements on one root table are refused; the old form `own` is retired and refused (`Z-M9`, remove the statement). Without login, without groups and in the login bounded context there is no protection (a statement rests there, without login or in the login bounded context it is refused). The root table of an existing aggregate never changes (a save with another table ends as a draft; create a new aggregate). Every read of the root table (single, multiple, list, delivered query with this root) carries the sight (`groups` filter, from the groups of the session) and counts capped; a new record of that table is created together with its access entries; every write door (update, delete, child operations) asks the access check once before it writes (no sight is the 404 of an unknown key, a level too low the 403 `forbidden`; `edit`, `all` for deleting the root; a dependent aggregate is asked at its owner with `edit`, and at the new owner too when a change moves it) and deleting the root removes its entries. The groups come from the project setting `groupLookup` (class fulfilling `JardisSupport\Contract\Auth\GroupLookupInterface`) or `groupDoors` (read doors); without it (or without login) there is no sight and nothing fails. The sight sits only at the root: a join partner, a child table, a `depend` target and the reload carry none and are not refused (a query root on a child table carries none; an aggregate root on that table makes it a protected root table). Blockers `V-ACCESS-1` to `-4` (`-3` also: one protection per root table) and `-7` (`-5` is vacant), warning `V-ACCESS-6` (read door at `open`). Exact forms and rules: skill `design-headless-mcp` |
| `writeOnly` | `[<column>…]` | written, never read (secret hash, one-time token hash): stays in the Create/Set/Add/Update commands, the validators and the OpenAPI request, and in persistence; absent from the Akte/Read DTO, list items, bulk read, event payloads, the OpenAPI response; it is no filter parameter of the seeded base list. A query that reads outward (stance `outside` or wider) may not filter or order on it (WO-2); never PK, public identifier, FK, adopt, computed or a `tenant`/`user`-marked column (WO-1). Only a query that reads inward (stance `closed` or `domain`) projects the column (family-internal read, e.g. a login or password-change check); no outer form ever carries it |
| aggregate without outer form (no key; a state of `Doors.json`) | every read row of the aggregate's block `closed` (gesture `closeReads` of `save_doors`) | no `{agg}()`/`{Agg}Read` on the BC facade (it stands only while a read way, the base list or a declared root query of the block is at least `domain`), no route, no OpenAPI path. Still fully usable family-internally (kernel seam, processes, closures). A foreign BC's `consumedCalls` onto a door that is missing or `closed` is a blocker (V-CONSUMED-EXISTS); a `ref` field of a process answer whose aggregate has no read door in the reader's world (neighbour BC: stance `domain` or wider, HTTP: `outside` or wider) is left out of the outer form (it stays inside); no finding. The key `visibility` is retired: V-DOOR-0 (MCP `save_aggregate` `graph.visibility`, `rename_aggregate` `visibility` are refused with a hint naming `save_doors`) |
| `eventIdentifier` | `{kind: pureJoin\|businessKey\|dependTarget\|syntheticPk}` | identifier in the event payload; undeclared → EVT-ID-3 suggestion. MCP only via `write_definitions` (no UI) |
| `orderBy` (node) | column + `ASC`/`DESC` | copied into the derived follow-up query of that child and orders it; an effect on the aggregate load path is not verified |
| `field` (node) | column list | column restriction; MCP only via `write_definitions` (no UI) |
| `validationOverrides` (aggregate) | `{rule, target, reason}` | silences warnings of this file; MCP only via `write_definitions` |
| Root remove | implicit | cascades through all children, FK-safe, in one transaction |
| Nesting | `many` under `many` at most 2 deep; multi-parent allowed when the same table backs the repeated entity | deeper nesting is rejected (A11) |
| Aggregate size | more than 6 distinct tables | hint only (A18) — a signal to split |
