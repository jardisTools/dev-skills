#### Continuation §2 — step 3: format markers of `save_aggregate` (`tenant`/`user`, `access`, `writeOnly`)

   - `tenant` / `user` (any entity, root AND child; omit = keep, `""` / `{}` = delete): `tenant` names the ONE column holding the tenant of the signed-in user, `user` maps columns to `onCreate` / `onWrite` (the bare id of the signed-in user; `onCreate` = Create only). The value comes from the request context, never from the client; the column leaves every input contract and is set at every write door; only `tenant` also filters the read doors, `user` is a write value. Columns must be varchar/char/uuid/integer data columns, not PK, key, adopt, computed (`V-TENANT-2`). A child entity that takes over the effective tenant column of an ancestor via `adopt` (transitively over the levels) is already tenant-filtered by derivation: every query rooted at it gets the automatic tenant filter, the value comes from `adopt`, not from the session, and a further marker on that `adopt` column is refused. The load echoes `tenantBlocked` / `userBlocked`, ignored on save. In a world with login (`middleware` carries `session`) every aggregate root needs a `tenant` marker (`V-TENANT-1`, Blocker; exempt: a BC with `loginIdentity: true`).
   - A query at the stance `outside` on a tenant-marked root (or on an entity derived tenant-filtered via `adopt`) needs no tenant filter of its own: the generated `{Query}Filter` takes `tenant` as first constructor argument and every lookup is scoped; the query value `{user: true}` binds the signed-in user (without login the blocker `V-TENANT-3`).
   - `access` (the aggregate ROOT only, never a child; omit = keep, `""` = delete): **protection is the rule, `access` is only the exception.** In a world that protects - login AND groups (project setting `groupLookup` or `groupDoors`) AND a bounded context WITHOUT `loginIdentity` - every root table carries the per-record sight on its own, and a root WITHOUT `access` is protected; you do not switch it on. Without login, without groups, or in the login bounded context nothing is protected (no sight, no number), and a statement rests without a finding (only without login and in the login bounded context it is refused). The protection belongs to the ROOT TABLE, not to one aggregate: several aggregates on the same root table are allowed, they carry the SAME statement (none, `everyone` or the same owner/via pair), and every one of them reads (list, single, multiple, query) and creates (entries) under the sight and the number of that table. Exactly two forms. `"access": "everyone"`: the aggregate is released, its records are visible to everyone in the tenant, the root table carries no sight and no number. `"access": {"owner": "<Aggregate>", "via": "<column>"}`: the aggregate takes over the sight of its owner, an aggregate of the SAME bounded context whose root table is protected (the owner itself is not released), through a column of its root; no number of its own (it reads under the number of its owner's table). The old form `"access": "own"` is RETIRED: every load door and `save_aggregate` refuse it (rule `Z-M9`, hint "remove the statement, protection is the rule"), no migration on open. The root table of an existing aggregate never changes: a save with another table ends as a draft (`Draft.json`), the answer names the reason and "create a new aggregate"; the first save of an empty aggregate sets it.
     The numbers: a protected root table gets ONE number in the access-type list of the domain, read back (read only) in `jardis://domain/{domain}/manifest` under `access.types` as `[{id, aggregate: "<Subdomain>.<BC>.<Aggregate>", retired}]`; one reconciliation keeps it, and every door that changes the model or the world calls it (save, delete, duplicate, `write_definitions`, the CLI `definition:build`, blueprint import, `update_project_settings`, every build). A second aggregate on the same table shares the number, a copy shares the number of its source's table; releasing or deleting the aggregate that carries the row hands the row to the next holder of the table, the number is retired only with the last one and never comes back; switching groups off and on again retires nothing; renaming keeps the number. Every other form is refused: a form other than the two, or a marker below the root (`V-ACCESS-1`); a statement in a world without login or in the login bounded context (`V-ACCESS-2`); an owner of another bounded context, an owner that is released, a `via` that is no root column, or different statements on one root table, because the protection of a root table is unambiguous (`V-ACCESS-3`; the same statement on several aggregates stays allowed); a protected root table without exactly one living number in the list (`V-ACCESS-4`); a read door of an aggregate on a protected root table at the stance `open` (`V-ACCESS-6`, warning: without a person the door answers no records); a delivered query whose root is a protected root table and whose `limit` exceeds the count cap of `jardissupport/acl` (`V-ACCESS-7`). `V-ACCESS-3` and `-4` judge only where the world protects. There is no rule `V-ACCESS-5`: the sight is checked only at the ROOT (the root table of the aggregate and the root entity of a query, and only when that root table is a sight table).
     A joined entity, a child table, a `depend` target and the reload carry no sight and are not refused; what comes along behind the root is decided by the modeller of the query or aggregate (the door decides who executes, the sight decides at the root row which rows come). A query root on a child table carries no sight; an aggregate whose root lies on that table makes it a root table, protected by the rule. Writing asks as well: every write door of a protected root (update, delete, child operations, `Set`, `Remove`) asks the access check once before it writes, from the groups of the session and only when the caller is a session (internal callers, processes, the owner `*` and a `seeAll:` entry of the door ask nothing): no sight is the same 404 as an unknown key, a level too low (`edit`; `all` for deleting the root) is the 403 `forbidden` of the domain; a dependent aggregate (`{"owner", "via"}`) is asked at its owner with `edit`, also when deleting, and when a change hangs it on another owner that owner is asked too (`edit` at both); deleting a root removes exactly its access entries. There is no locking: between the question and the write a revocation can fall. The aggregate load returns the stored marker. Example (a released aggregate): `{"id": "n1", "table": "countries", "entityKey": "country", "access": "everyone"}`.
   - `writeOnly` (omit = keep, `[]` = delete): written, never read from outside — absent from the record read (UI term "Akte"), public list, bulk read, events and the OpenAPI response, present in the write contract. Only a query that reads inward (stance `closed` or `domain`) projects it (family-internal read, e.g. verifying a stored digest). A query that reads outward (stance `outside` or wider) may not filter or order on it (`WO-2`); not the PK, key, FK, adopt, computed or a `tenant`/`user`-marked column (`WO-1`).
   - `graph.visibility` is RETIRED (also `rename_aggregate` `visibility`): the call is refused with `V-DOOR-0` and a hint naming `save_doors`. An aggregate without any outer door is the state in which every read row of its block in `Doors.json` is `closed` (gesture `closeReads`): no `{agg}()`/`{Agg}Read` on the BC facade (it stands only while a read way, the base list or a declared root query of the block is at least `domain`), no route, no OpenAPI path; reads and writes stay possible family-internally through the kernel seam and through a process of the BC. Cross-BC access goes through a read door of the owner at `domain` or wider (its `{Agg}Read`), and cross-BC writes through the target BC's `process()` or a command door at `domain` or wider (`{BC}::{command}()`); a `consumedCalls` entry or sub-process node onto a door that is missing or stands `closed` is `V-CONSUMED-EXISTS` (blocker); a `ref` field of a process answer whose aggregate has no read door in the reader's world (neighbour BC: stance `domain` or wider, HTTP: `outside` or wider) is left out of the outer form and stays inside; no blocker, no warning (nobody outside could reload it). The former `V-AGG-VIS-1`…`5` are gone.
   - Blockers come back in `valid` / `errors` of the save answer; check them (the aggregate is written regardless).
   - The request attributes are `RequestAttribute::SUBJECT_ID`, `::TENANT` (`jardisTenant`) and the rights claim `::RIGHTS` of `jardissupport/contracts` >= 2.17; the authenticating middleware of the app sets them. In a world with per-record protection (protection is the rule, see `access` above) the group middleware add `::GROUPS` (`list<int>`, `jardisGroups`), `::PERSONAL_GROUP` (`int`), `::FALLBACK_GROUPS` (`array<int, int>`, information kind => group) and `::SHARE_TARGETS` (group => level word, or `false` when a target cannot be resolved), see `jardis://root` setting `groupLookup` or `groupDoors`. Every read route of a protected root fills its `groups` filter from `GROUPS` (absent = no group = the empty list = no records; only the owner `*` or a `seeAll:` entry the rule of the door accepts - `seeAll:<right of the route>`, or `seeAll:<resource>:*` for every door of the resource - sees all); none of this appears as a parameter in the OpenAPI contract. The create door of a protected root takes ONE optional request header, `X-Jardis-Share-With: 12=view, 15=edit` (comma-separated `group=level`, level one of the words `view`, `edit`, `all`): the new record is created with an entry `all` for the personal group of the caller (without one: the fallback group of the information kind) and one entry per named group; a missing or unknown level answers 400 under the header name, a group that cannot be resolved answers 404; the header exists only at that operation, a process door has none. Sending nothing is valid. A route whose right is missing answers 403 `access.rightMissing` (`context.right`) from `RequireRight`, one whose required attribute is absent 403 `request.attributeMissing` (`context.attribute`) from `RequireRequestAttribute` (`jardiscore/app` >= 3.0 for `RequireRight`, >= 1.8 for `RequireRequestAttribute`) before the handler — never 500; the OpenAPI contract names both.
   - A process input field takes no request attribute: `requestAttribute` is no format term any more, not even the former `session` marker (a leftover field of an older workspace is refused when the process loads, with the existing rule id Z-M2; nothing is migrated on open). Tenant and user are no declared input: in a world with login the door fills the fields `tenant`/`user` of the process input and a node reads `$ctx->input()->tenant` / `->user`; a Rule node on a tenant-marked root takes its scope from there, with no scope-source field.
