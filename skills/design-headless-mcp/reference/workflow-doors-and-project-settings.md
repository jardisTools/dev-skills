#### Continuation §2 — doors, middleware and project settings

**Doors and the middleware pipeline (app-wide HTTP pipeline, `jardiscore/app` >= 3.2).** The door stances (`Doors.json`) and the project settings steer who may call a generated route:
- **Project setting `middleware`** — `update_project_settings` takes `middleware`: an ordered list of names; an entry without a backslash is a standard name (today only `session`), an entry with a backslash is a project class (FQCN, constructor `__construct(DomainKernelInterface $kernel)` or none). Never set = `["session"]` (the default, session guard on; it needs the env key `AUTH_TOKEN_KEY` - base64 of 32 random bytes - in the project `.env`, the access token is signed by `jardissupport/auth` >= 1.5); `[]` = deliberately no pipeline; omit the field = stored value untouched. Names are not checked at save time, a wrong one fails at app start. Read back the EFFECTIVE list: Resource `jardis://root` (field `middleware`) and `jardis://project` (field `middlewareEffective`; `manifest.middleware` is the stored value, absent when never set). The next `build` writes `src/App/middleware.php`; an older `src/App/bootstrap.php` without the `'middleware'` entry is never overwritten (the build warns).
  `update_project_settings` `{"middleware": ["session", "App\\Middleware\\AuditTrail"]}` (session first: it must run before any middleware that reads session attributes) · `{"middleware": []}` · `{"middleware": ["session"]}` (explicit default).
- **Door stances — `Doors.json` and the tool `save_doors`.** Who may reach a door is ONE switch per door, the **stance**, stored as a row in the per-bounded-context file `Doors.json` (next to `Queries.json`, `Closures.json`, `ValueLists.json`): `closed` (only the own BC) · `domain` (the facades of the other BCs of the domain; no route, no right) · `outside` (route, OpenAPI path and right; session + right) · `open` (no login, no right; **process rows only**). Rows are the aggregate blocks (read ways `{agg}ById`/`{agg}ByIds`, or with a public unique key only `{agg}By{Key}`/`{agg}By{Key}s`; base list `{agg}List`; declared queries of the root entity; commands by class name `Create{Agg}`, `Update{Agg}`, …) and the block `process`. The row is named like the facade method. Defaults without a row: read ways and base list `outside`, declared query `closed`, command `closed`, process `outside`; the build adds missing rows, never removes one. Query on a child entity: no row, always `closed`. A command at `domain` or wider is the facade door `{BC}::{command}()`; `Create{Agg}` at `outside` also gets `POST /{bc}/{agg-plural}`. Guards (`bindings.{cmd}.chain`) apply in every stance.
  - **Read first:** Resource `jardis://doors/{domain}/{subdomain}/{bc}` = every door of the model with block, kind, name, stored stance, default, effective stance, route and right, plus the orphan rows (`V-DOOR-1`) and the `mtime` of the file; Resource `jardis://doors/{domain}` = the domain-wide view per BC (kind, stance, effective stance, door name).
  - **Write:** `save_doors` {domain, subdomain, bc} with EXACTLY ONE of three forms: `rows` [{block, row, stance}] (+ `remove` [{block, row}] only for an orphan row) · `blocks` (the whole file as [{name, rows:[{key, value}]}], also the repair of a file that cannot be parsed) · `gesture` `closeReads` | `defaults` (+ `aggregate`, `dryRun`). Pass the last-seen `mtime` (`force: true` overrides). Refusals: a value outside the vocabulary, or `open` on a non-process row = 422 `V-DOOR-0` (never stored); a row that names no door = 404; removing a row that belongs to a door = 422 `V-DOOR-1`; `Doors.json` changed since `mtime` = 409 `CONFLICT`. A gesture that finds the state already reached writes nothing and answers `note: "alreadyDone"`. Rebuild the BC afterwards: the stances become facades, routes, OpenAPI and rights.
  - **Access rows (kind `access`).** At the aggregate that holds the living access number of a protected root table (not at an inheriting, released or unprotected aggregate) the door list carries exactly three rows: `Share{Agg}`, `Unshare{Agg}` and the information door `{agg}Shares` (default `outside`; `open` is `V-DOOR-0`; a name equal to a command or query is `V-QDEF-23`). From `domain` the BC facade has `share{Agg}()`, `unshare{Agg}()` and `{agg}Shares()` (a process node of the own BC calls `Share{Agg}`, see `workflow-process-modelling`); from `outside` also the routes `POST /{bc}/{root}/{key}/share{Agg}` and `…/unshare{Agg}` (body `groups` ints and/or `person`, `level` one of `view|edit|all` at share only) and `GET …/{key}/{agg}Shares` (items `[{group, level}]`), each with its own right (`{bc}.{agg}:share{Agg}`, …). The caller needs level `all` on the record (403 `forbidden` below it, 404 without sight); the last entry with `all` cannot be taken away or lowered (422 `RuleViolation`, table unchanged). `closed` = no door at all. Written with `save_doors` like any other row; read with `jardis://doors/…`. Responsibility ("assign") is modelled as a process that calls `Share{Agg}`, there is no assign door.
  - **Retired switches:** `visibility` (aggregate graph, query, process), `subprocessOnly` (process), `expose` (a `bindings` entry) and the project setting `openRoutes` are no longer read; a call that carries one (`save_aggregate`, `rename_aggregate`, `save_queries`, `save_closures`, `save_process`, `update_process_metadata`, `update_project_settings`, also the validate/preview/probe variants) is refused with `V-DOOR-0` and a hint naming `save_doors`, a file that still carries one is a blocker `V-DOOR-0`. Mapping: aggregate `internal` → every read row `closed`; query `internal`/`public` → `closed`/`outside`; `expose: true` → the command row `outside`; `subprocessOnly` → process row `closed`; process `visibility: internal` → `domain`; `openRoutes` → process row `open`. A process route is open (registered `$routes->anonymous()->{verb}(…)`, no session, no right, no `security` in the OpenAPI) exactly when its row is `open`; an open process reaches no tenant-marked aggregate (`V-ROUTE-OPEN-TENANT`). In an app without login `open` and `outside` coincide; a stored `open` row reads as `outside` with the hint `V-DOOR-3`.
- **Project setting `sessionProcesses`** — `update_project_settings` takes `sessionProcesses`: the processes of the session life cycle by role, `{signIn, signOut, switchTenant}`, each `{bc, process}` (BC and process must exist and sit in the `loginIdentity` BC, 422 otherwise; the Access blueprint pre-fills it). The `signOut` / `switchTenant` route additionally revokes the session (`RevokeSessionOnSuccess`); an open route marked this way is a build error. From `signIn` + `switchTenant` the build writes `Api/{Domain}/system.php` (the system run over `SignedInRun`; env `SYSTEM_SIGN_IN_SECRET`).
- **Project setting `groupLookup`** — `update_project_settings` takes `groupLookup`: the fully qualified name of the project class that fulfils `JardisSupport\Contract\Auth\GroupLookupInterface` (the answers: the groups of a person within a tenant, the personal group, which named groups exist, the fallback group of an information kind). A domain has sight as soon as the world protects (login, `groupLookup` set, bounded context without `loginIdentity`) and a protected root table holds a living number - protection is the rule, no aggregate needs a marker (`access: "everyone"` releases one); then `src/App/middleware.php` carries `ResolveGroups` directly behind `session` (reads the groups of the signed-in person into the request), `ResolveFallbackGroups` behind it (over the information kinds of the domain) and `ResolveShareTargets` at the create door of each protected root, all built over that one class (or over the doors, see `groupDoors`). Without the setting (or without login) there is no sight, no number and no group middleware, nothing fails at app start and the file stays as it was; setting it (or switching login on) makes `update_project_settings` reconcile the number list of the domain. A wrong class name is not checked at save time, it fails at app start. Omit the field = stored value untouched, an empty name removes it. Read back: Resource `jardis://root`. The class is project code in `App/` (it answers the group questions from the project's own group tables); the per-record sight itself stays in `jardissupport/acl`.
- **Project setting `groupDoors`** — the same contract through read doors instead of a class: `update_project_settings` takes `groupDoors`, one `{bc, door, params, answer, personal?}` per question — `groupsOfSubject` (the groups of a person in a tenant), `personalGroup`, `groupsByIds` (the groups of a tenant by ids), `fallbackGroup` (the fallback group of an information kind); a question you do not set stays unset. Every named door must be a query of an existing bounded context whose stance is at least `domain` (422 otherwise); `params` binds each fixed contract value to exactly one declared parameter of the door (`groupsOfSubject`: subject, tenant, now; `personalGroup`: subject, tenant; `groupsByIds`: ids, tenant; `fallbackGroup`: type, tenant); `answer` names the result field that carries the group number; `personal {field, value}` stands on `groupsOfSubject` only and marks the personal group among its rows. A wrong assignment is 422 (location `groupDoors.<question>.params|personal|answer`), nothing stored; class and doors set together is 422 too (clear the other form in the same call: `groupLookup` `""` or `groupDoors` `{}`). With complete doors `src/App/middleware.php` builds ONE `GroupDirectoryFromDoors` from the door calls instead of the class, incomplete doors give a build warning and no group middleware. Never set = none: a blueprint import such as Access pre-fills it once, only when neither form was ever set; `{}` = deliberately none. Read back: Resource `jardis://root` (`groupDoors`).
- **Project setting `backfillPrelude`** — `update_project_settings` takes `backfillPrelude`: `{bc, process, repeatWhile?}`, the one process that runs before the backfill of the access entries of records that existed before protection (`bin/console access:backfill` / `make access-backfill` of the app template runs the generated `Api/{Domain}/backfill.php`; it exists when a root table has its own protection). `repeatWhile` names an integer field of the process answer: the prelude is repeated while it is above zero. Omit = untouched, `{}` = remove; 422 (location `backfillPrelude`) for an unknown BC or process, a required input, stance `closed`, or a way that reaches a tenant/user marked aggregate outside the login BC (`V-BACKFILL-PRELUDE-TENANT`: the prelude runs without a session). The Access blueprint pre-fills it once. Read back: Resource `jardis://root` (`backfillPrelude`). Output, exit codes and the fallback-group rule: `generated-code-wire-transport`.
- **Rights list** — every route at `outside` in a login world is one right per door (`{bc}.{aggregate}:{row}`, the row name of the door, e.g. `sales.order:orderList`, `sales.order:createOrder`; `{bc}.process:{name}` for a process); a process at `open` has no right; the list is `Api/{Domain}/rights.json` and the Resource `jardis://domain/{domain}/rights` byte for byte (a model with `V-RIGHT-1..2` blockers answers 422). Whether a door is granted to anyone is data (the roles); the build reads no body for it. The Resources `jardis://doors/{domain}/{subdomain}/{bc}` and `jardis://doors/{domain}` list every door with its stance and effective stance — read them and the rights to verify what is reachable from where, and which right opens what, before building.
